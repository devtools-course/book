= Сети и DNS в Docker
:page-authors: Михаил Агафонов
:description: Сетевая изоляция контейнеров, пользовательские bridge-сети, встроенный DNS Docker, прямое подключение host, режим none и частые проблемы
:icons: font

До сих пор мы запускали контейнеры поодиночке и пробрасывали порты через флаг `-p`, чтобы открывать их в браузере на своём компьютере. Но в реальной работе контейнеров почти всегда несколько, и они должны взаимодействовать друг с другом по сети. В этой статье разберем, как связать контейнеры между собой, почему не стоит полагаться на сеть по умолчанию и как устроен встроенный DNS Docker.

== Сетевая изоляция в Docker

По умолчанию каждый контейнер запускается со своей собственной изолированной сетью. У него свой личный `localhost` (`127.0.0.1`) и независимое пространство портов: например, можно запустить десять разных контейнеров, и каждый из них сможет слушать порт `80` на своём локальном интерфейсе, совершенно не мешая остальным.

Чтобы эти изолированные контейнеры могли передавать данные друг другу и выходить в интернет, Docker объединяет их в виртуальные сети.

Управлять сетевым поведением контейнера можно через флаг `--network`. На одном хосте чаще всего используют три режима:

* **`bridge`** (по умолчанию)  --  контейнер подключается к изолированной виртуальной сети на хосте.
* **`host`**  --  сетевая изоляция отключается, контейнер напрямую использует порты и сетевые интерфейсы хоста.
* **`none`**  --  сеть полностью отключена, у контейнера нет внешней связи.

== Основной режим: сети bridge

Основной режим сети в Docker называется **`bridge`** (мост). Это виртуальная локальная сеть внутри вашей машины, к которой подключаются контейнеры. При этом важно различать два варианта: **стандартную сеть** и **пользовательские сети**.

=== Стандартная сеть (default bridge)

Если запустить контейнеры без указания флага `--network`, они попадают в общую стандартную сеть:

[,console]
----
$ docker run -d --name app1 alpine sleep 1000
$ docker run -d --name app2 alpine sleep 1000
$ docker exec app1 ping -c 1 app2
ping: bad address 'app2'
----

В стандартной сети **нет поиска по именам (DNS)**. Контейнеры могут обращаться друг к другу только по прямым IP-адресам (например, `172.17.0.3`). Но опираться на IP нельзя: при каждом перезапуске или пересоздании контейнера его IP-адрес меняется.

[NOTE]
Раньше для связи в стандартной сети использовали флаг `--link`, который вручную дописывал IP-адреса соседей в `/etc/hosts`. Этот механизм давно устарел (deprecated) и не используется в современной разработке.

=== Пользовательские сети (user-defined bridge)

Правильный и стандартный способ связать сервисы  --  создать собственную именованную сеть командой `docker network create`:

[,console]
----
$ docker network create my-net
$ docker run -d --name web --network my-net nginx:alpine
$ docker run --rm --network my-net alpine wget -qO- http://web:80
----

В этом примере видны две важные вещи:

1. Контейнер `alpine` успешно отправил запрос **прямо по имени `web`**, не зная его IP-адреса.
2. При запуске `web` **не использовался флаг `-p`**. Внутри одной сети контейнеры общаются между собой напрямую по внутренним портам приложений. Флаг `-p` нужен исключительно для того, чтобы открыть порт наружу  --  на ваш физический компьютер (например, чтобы открыть сайт в браузере).

=== Встроенный DNS Docker

Связь по именам контейнеров обеспечивает встроенный DNS-сервер Docker, который автоматически работает во всех пользовательских сетях:

* Демон Docker слушает служебный адрес `127.0.0.11` и автоматически прописывает его в сетевые настройки (`/etc/resolv.conf`) каждого подключенного контейнера.
* Запросы к именам соседних контейнеров демон моментально сопоставляет с их текущими внутренними IP-адресами.
* Запросы к внешним сайтам в интернете автоматически перенаправляются на DNS-серверы вашего хоста.

Кроме базовой связи по именам, пользовательские сети дают ещё три важных преимущества:

* **Сетевые алиасы (`--network-alias`):** контейнеру можно назначить дополнительное имя. Если дать один и тот же алиас нескольким контейнерам (например, двум копиям приложения), встроенный DNS будет автоматически распределять запросы между ними по очереди (механизм балансировки DNS Round-Robin).
* **Изоляция проектов:** контейнеры из разных сетей изолированы друг от друга и не могут обмениваться трафиком, даже работая на одной машине.
* **Подключение к нескольким сетям:** один контейнер можно подключить сразу к двум и более сетям командой `docker network connect <сеть> <контейнер>`. В каждой из сетей он получает отдельный IP-адрес и становится доступен соседям по имени. Это позволяет использовать один контейнер как связующее звено между двумя изолированными группами сервисов.

== Альтернативные режимы: host и none

=== Прямой доступ к сети хоста (--network host)

В режиме `host` Docker полностью отключает сетевую изоляцию:

[,console]
----
$ docker run -d --network host nginx:alpine
----

Контейнер использует сеть вашего компьютера напрямую. Как следствие:

* Флаг `-p` не нужен: порт контейнера сразу открывается на самом хосте.
* Нельзя запустить на одном порту два сервиса даже в разных контейнерах (возникнет ошибка `Address already in use`).
* Соединение не теряет в скорости из-за виртуализации сети.

Этот режим используют, когда сервису требуется открывать очень широкий диапазон портов, когда приложению нужно напрямую анализировать сетевой трафик хоста, либо в сценариях с экстремальными требованиями к производительности сети.

[NOTE]
На macOS и Windows контейнеры Docker выполняются внутри служебной виртуальной машины Linux, поэтому `--network host` связывает контейнер с сетью этой виртуальной машины, а не вашего основного компьютера.

=== Полная сетевая изоляция (--network none)

В режиме `none` Docker полностью отключает сеть: у контейнера нет внешних сетевых интерфейсов, доступен только внутренний `localhost` (`127.0.0.1`).

Такой контейнер гарантированно не сможет отправить или получить данные из сети. Этот режим используют при запуске потенциально опасного кода, а также для исключения любых утечек данных.

== Типичные проблемы и диагностика

=== Сервис не открывается с хоста (127.0.0.1 против 0.0.0.0)

Частая ошибка: вы запустили контейнер с `-p 8080:8080`, но сервис не отвечает в браузере.

Причина в том, на каком адресе сервер внутри контейнера ожидает входящие соединения. Если в коде указан `127.0.0.1` (localhost), сервер будет принимать запросы только от процессов внутри своего контейнера. Трафик от проброшенного порта хоста (`-p`) приходит на внешний интерфейс контейнера, поэтому приложение внутри контейнера обязано слушать адрес `0.0.0.0` (то есть принимать подключения со всех сетевых интерфейсов).

=== Доступ к сервисам хоста (host.docker.internal)

Имя `localhost` внутри контейнера указывает на сам контейнер, а не на вашу основную систему. Чтобы достучаться из контейнера до сервиса на вашем компьютере, в Docker принято использовать имя **`host.docker.internal`**.

На Linux Docker не добавляет это имя автоматически. Чтобы оно заработало, при запуске передают флаг `--add-host`:

[.wrap,console]
----
$ docker run --rm --add-host=host.docker.internal:host-gateway alpine curl http://host.docker.internal:8000
----

Флаг `--add-host` добавляет строчку соответствия в файл `/etc/hosts` внутри контейнера. При этом ключевое слово `host-gateway` указывает Docker автоматически подставить туда реальный IP-адрес вашего компьютера.

=== Полезные команды диагностики

Для проверки состояния сетевого окружения используют две команды:

* **`docker network ls`**  --  выводит список всех существующих сетей на хосте (включая дефолтные `bridge`, `host`, `none` и созданные вами).
* **`docker network inspect <имя_сети>`**  --  показывает детальную информацию о сети: подсеть, шлюз и список всех подключенных контейнеров с их текущими IP-адресами.
