= Проверка состояния контейнеров (Healthchecks)
:page-authors: Михаил Агафонов
:description: Инструкция HEALTHCHECK, проверка готовности сервиса, статусы starting, healthy и unhealthy, параметры интервалов и диагностика
:icons: font

Команда `docker ps` показывает статус контейнера `Up`, пока жив его главный процесс с PID 1. Но живой процесс ещё не означает, что сервис внутри действительно функционирует исправно:

* База данных уже запустилась, но ещё 20 секунд инициализируется и отклоняет подключения.
* Приложение зависло и перестало отвечать на запросы, хотя сам процесс не упал.

В обоих случаях Docker показывает статус `Up`, считая контейнер работающим. Чтобы проверять реальную готовность сервиса, а не просто факт жизни процесса, нужен отдельный механизм  --  и такой механизм существует: **Healthcheck**.

== Инструкция HEALTHCHECK в Dockerfile

Инструкция `HEALTHCHECK` задает команду, которую Docker будет периодически запускать внутри контейнера для проверки его работоспособности.

Результат проверки Docker определяет по коду завершения команды:

* **Код `0`**  --  сервис здоров и готов принимать запросы (статус `healthy`).
* **Любой ненулевой код**  --  сервис неисправен (статус `unhealthy`).

Пример настройки проверки в `Dockerfile`:

[,bash]
----
FROM alpine:3.20
RUN apk add --no-cache curl

EXPOSE 8080

HEALTHCHECK --interval=10s --timeout=3s --start-period=15s --retries=3 \
  CMD curl -f http://127.0.0.1:8080/health || exit 1

CMD ["./my-app"]
----

В этой проверке:

* `curl http://127.0.0.1:8080/health`  --  делает локальный HTTP-запрос к приложению.
* Флаг `-f` (`--fail`)  --  заставляет `curl` возвращать ошибку, если сервер ответил HTTP-кодом ошибки (4xx или 5xx). Без флага `-f` `curl` вернет код `0` даже на ответ `500 Internal Server Error`.
* `|| exit 1`  --  стандартная конструкция командной строки: если `curl` завершился с ошибкой, принудительно вернуть код `1`.

=== Параметры: интервалы, таймауты и попытки

* **`--interval` (по умолчанию `30s`)**  --  как часто запускать команду проверки.
* **`--timeout` (по умолчанию `30s`)**  --  максимальное время ожидания ответа. Если команда зависла дольше этого времени, проверка считается проваленной.
* **`--start-period` (по умолчанию `0s`)**  --  время на стартовую инициализацию сервиса. Ошибки в этот период не учитываются в счетчике сбоев, но первый же успешный ответ сразу переводит контейнер из состояния `starting` в `healthy`.
* **`--retries` (по умолчанию `3`)**  --  сколько неудачных проверок подряд должно произойти, чтобы контейнер получил статус `unhealthy`. Одиночный сбой не меняет статус, если следующая проверка прошла успешно.

=== Отключение проверки (HEALTHCHECK NONE)

Если в базовом образе уже был прописан `HEALTHCHECK`, но в вашем контейнере он не нужен или мешает, его можно отключить:

[,bash]
----
HEALTHCHECK NONE
----

== Статусы здоровья и диагностика сбоев

=== Жизненный цикл: starting, healthy и unhealthy

После запуска контейнера в выводе `docker ps` в столбце `STATUS` отображается его состояние здоровья:

1. `Up 3 seconds (health: starting)`  --  контейнер только стартовал, идет стартовый период или первая проверка еще не завершилась.
2. `Up 20 seconds (healthy)`  --  проверка завершилась успешно с кодом `0`.
3. `Up 1 minute (unhealthy)`  --  проверка завершилась ошибкой `--retries` раз подряд.

[IMPORTANT]
====
Статус `unhealthy` **не перезапускает и не останавливает контейнер**. Docker лишь фиксирует факт сбоя.

Этот статус нужен для двух вещей:

* Чтобы при вызове `docker ps` сразу видеть аварийное состояние сервиса, а не обманчивый `Up`.
* Чтобы внешние инструменты автоматизации могли среагировать на проблему (например, Docker Compose умеет задерживать старт зависимых сервисов, пока база данных не станет `healthy`).
====

Если контейнер получил статус `unhealthy`, проверки **не прекращаются**: Docker продолжает запускать команду с интервалом `--interval`. Если сервис восстановит работу и команда вернет `0`, контейнер снова вернется в статус `healthy`.

=== Диагностика сбоев: docker inspect

Посмотреть точную причину сбоя и вывод команды последней проверки можно через `docker inspect`:

[.wrap,console]
----
$ docker inspect --format='{{json .State.Health}}' my-app
----

В секции `Log` вы увидите список последних проверок, их код завершения (`ExitCode`) и текстовый вывод команды (`Output`), что позволяет быстро понять, почему проверка завершилась ошибкой.

== Проверка здоровья в минимальных образах

В минимальных образах (`distroless`, `scratch`) часто нет утилиты `curl`. Ставить её только ради проверки не стоит  --  это раздувает образ лишними пакетами.

Вместо этого используют то, что уже доступно внутри контейнера:

* **Штатные утилиты сервисов**  --  во многих официальных образах уже есть встроенные инструменты проверки:
+
[,bash]
----
# Пример для PostgreSQL
HEALTHCHECK CMD pg_isready -U postgres || exit 1
----
* **Проверка флагом в бинарнике**  --  в образах `FROM scratch`, где нет ни командной оболочки, ни утилит, проверку зашивают прямо в исполняемый файл приложения:
+
[,bash]
----
HEALTHCHECK CMD ["/server", "--healthcheck"]
----
При вызове с таким флагом программа сама выполняет внутреннюю самопроверку и завершается с кодом `0` или `1`.

== Настройка и переопределение в docker run

Проверку здоровья можно настроить или переопределить без изменения `Dockerfile`  --  напрямую флагами команды `docker run`:

[.wrap,console]
----
$ docker run -d --name my-web \
    --health-cmd "curl -f http://127.0.0.1:80/ || exit 1" \
    --health-interval 5s \
    --health-retries 2 \
    nginx
----

А чтобы полностью отключить проверку, унаследованную из базового образа, передают флаг `--no-healthcheck`.
