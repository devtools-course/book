= Сборка образов и Dockerfile
:page-authors: Михаил Агафонов
:description: Декларативная сборка образов с помощью Dockerfile: контекст сборки, директивы, запуск процессов через ENTRYPOINT и CMD, кэширование слоев и оптимизация
:icons: font

В прошлых статьях мы запускали контейнеры из чужих готовых образов (`alpine`, `nginx`). Чтобы упаковать в контейнер собственный проект, нужно создать свой образ. В этой статье разберем, как устроен процесс сборки, как правильно описывать его в файле `Dockerfile` и как эффективно управлять слоями и запуском приложений.

== Как создается образ

Процесс создания собственного образа строится вокруг трех вещей:

1. **Контекст сборки (Build Context)**  --  папка на вашем компьютере, в которой лежат все необходимые файлы для сборки: исходный код, конфигурации, списки зависимостей.
2. **`Dockerfile`**  --  текстовый файл, находящийся в этой папке. Это буквально пошаговая инструкция по созданию образа.
3. **Команда `docker build`** берет контекст сборки, построчно читает инструкции `Dockerfile` и шаг за шагом формирует неизменяемые слои (`lowerdir`) нового образа.

На выходе получается готовый **образ**, представляющий собой набор неизменяемых слоев и конфигураций, которые сохраняются в локальном хранилище Docker, их можно вывести командой `docker images`. Из этого образа затем запускаются контейнеры через `docker run`. Если они не найдены в локальном хранилище, `docker run` автоматически попытается подтянуть их из облачного реестра.

Разберем каждый из этих элементов подробно.

=== Контекст сборки и команда docker build

Сборка запускается командой `docker build`:

[,console]
----
$ docker build -t my-app:1.0 .
----

* Флаг **`-t` (tag)** маркирует образ в формате `имя:тег`:
** **Имя**  --  название сервиса или проекта.
** **Тег**  --  метка конкретной сборки образа. Чаще всего это версия (`1.0`) или вариант сборки (`alpine`, `slim`). Если опустить тег (`-t my-app`), Docker подставит `latest`.
** Без флага `-t` образ останется безымянным: `<none>` в `docker images`, и обращаться к нему придется по хэшу `IMAGE ID`.
* Точка в конце команды указывает путь к **контексту сборки**.

[IMPORTANT]
Точка указывает не просто на место, где лежит файл `Dockerfile`, а на директорию хоста, которую клиент Docker **упакует в tar-архив и передаст демону Docker** по сокету `/var/run/docker.sock`. Если запустить сборку в каталоге с тяжелыми папками (`node_modules`, `.venv`, репозиторием `.git`), клиент потратит лишнее время на передачу сотен мегабайт демону еще до выполнения первой строчки `Dockerfile`.

=== Файл .dockerignore

Чтобы исключить лишние файлы из передачи демону, рядом с `Dockerfile` создают файл `.dockerignore` (работает аналогично `.gitignore`):

[,text]
----
.git
.gitignore
README.md
*.tmp
.env
.venv
node_modules/
target/
build/
----

Все перечисленные файлы и маски не попадут в контекст сборки. Это ускоряет сборку и предотвращает случайную утечку паролей или секретов из локального файла `.env` в публичный образ.

== Создаём Dockerfile

Для лучшего понимания происходящего в этом разделе стоит держать в голове, что наша цель  --  создать новый образ, представляющий собой *набор файлов*, который будет смонтирован как файловая система изолируемого процесса. Docker хранит этот набор файлов как неизменяемые слои в `lowerdir`. Каждая строчка в `Dockerfile`, меняющая файлы на диске, создает новый неизменяемый слой.

Ранее мы сказали, что образ  --  это набор файлов, однако это не совсем так. Образ содержит в себе еще и **метаданные**: какую команду запускать по умолчанию, переменные окружения, рабочую директорию, пользователя и список открытых портов. Эта информация также упаковывается в образ при помощи инструкций `Dockerfile`.

Типичный рабочий `Dockerfile` выглядит следующим образом:

[,bash]
----
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

ENV PORT=8080
EXPOSE 8080

CMD ["python", "main.py"]
----

Разберем назначение каждой директивы по порядку:

=== FROM
Обязательная первая инструкция. Задает базовый родительский образ, поверх слоев которого будет производиться сборка:

[,bash]
----
FROM ubuntu:24.04
----

=== RUN
Выполняет команду на этапе сборки и сохраняет изменения файловой системы в виде нового неизменяемого слоя:

[,bash]
----
RUN apt-get update && apt-get install -y curl
----

=== WORKDIR
Задает рабочую директорию как для инструкций сборки, так и для самого процесса при последующем запуске контейнера. Если указанная папка не существует, Docker создаст ее автоматически:

[,bash]
----
WORKDIR /app
----

[IMPORTANT]
Не используйте `RUN cd /app` для перехода в нужную папку, эффект команды `cd` исчезнет сразу по завершении текущей строки.

=== COPY vs ADD
Обе инструкции копируют файлы с хоста (из контекста сборки) внутрь файловой системы образа:

* **`COPY`**  --  простое и предсказуемое копирование файлов или папок:
+
[,bash]
----
COPY config.json /app/config.json
----
* **`ADD`**  --  расширенная инструкция. Умеет автоматически распаковывать локальные tar-архивы , а также скачивать файлы по URL.

Всегда используйте `COPY`. Инструкция `ADD` нужна только специфических случаях  --  когда требуется скопировать локальный tar-архив и автоматически распаковать его в корень образа или скачать файл из сети.



=== ENV
Задает переменные окружения, которые будут доступны как на этапе дальнейшей сборки, так и при последующем запуске контейнера из этого образа:

[,bash]
----
ENV PORT=8080
ENV APP_ENV=production
----

=== EXPOSE
Информирует, какие сетевые порты планирует слушать приложение внутри контейнера:

[,bash]
----
EXPOSE 8080
----

`EXPOSE` носит исключительно уведомительный характер. Он **не открывает доступ к порту на хосте** и не делает его публичным. Чтобы порт действительно заработал снаружи, его все равно нужно пробросить через флаг `docker run -p 8080:8080`.

=== USER

По умолчанию все команды при сборке и в запущенном контейнере выполняются от суперпользователя `root`. Так как Docker по умолчанию не изолирует пользователей через User Namespaces, UID 0 внутри контейнера равен реальному UID 0 на хосте. При уязвимости в коде, побеге из контейнера или через примонтированные файлы злоумышленник получит права root на хостовой системе.

Инструкция `USER` задает числовой `UID:GID` (или имя созданного пользователя), от которого будут выполняться последующие команды `RUN`, а также запускаться `ENTRYPOINT` и `CMD`:

[,bash]
----
RUN useradd -m -u 1001 appuser
USER appuser
----

=== Запуск процессов: ENTRYPOINT, CMD

Какой именно процесс будет запущен внутри контейнера определяется директивами `ENTRYPOINT` и `CMD`. Они склеиваются просто как строки в единую команду запуска. По задумке:

* **`ENTRYPOINT`**  --  исполняемый файл программы, который запускается при старте.
* **`CMD`**  --  аргументы по умолчанию, передаваемые в `ENTRYPOINT`. 

Внутри контейнера процесс будет запущен командой, полученной простой конкатенацией `ENTRYPOINT + CMD`. Если после `docker run [OPTIONS] IMAGE_NAME` ничего не указано, то `CMD` останется таким, как был указан в `Dockerfile`. Однако при запуске контейнера можно подменить `CMD`, указав нужные параметры после названия образа.

Рассмотрим пример:

[,bash]
----
ENTRYPOINT ["ping"]
CMD ["localhost"]
----

1. **Запуск по умолчанию:**
+
[,console]
----
$ docker run my-ping
----
Аргументы не переданы, поэтому берется `CMD` из образа. Выполнится: `ping localhost`.

2. **Переопределение `CMD`:** любые аргументы, переданные в конце `docker run`, **полностью замещают `CMD`**:
+
[,console]
----
$ docker run my-ping ya.ru
----
Значение `ya.ru` заменит дефолтный `localhost`, и выполнится: `ping ya.ru`.

3. **Переопределение `ENTRYPOINT`:** если нужно заменить саму исполняемую программу (например, чтобы зайти в shell), используют флаг `--entrypoint`:
+
[,console]
----
$ docker run --rm -it --entrypoint sh my-ping
----

[NOTE]
Если `ENTRYPOINT` в образе не задан, то после конкатенации базовой программой для запуска становится первый элемент из `CMD`. Поэтому `ENTRYPOINT` часто опускают и пишут просто `CMD ["python", "main.py"]`.

=== Exec-форма против Shell-формы

В `CMD` и `ENTRYPOINT` команды можно передавать массивом (`CMD ["python", "app.py"]`  --  Exec-форма) или строкой (`CMD python app.py`  --  Shell-форма). 

Shell-форма не рекомендуется: она неявно запускает шелл `/bin/sh -c`. **Всегда используйте Exec-форму в квадратных скобках.**

== Послойная сборка и переиспользование слоев

Как именно Docker собирает образ по инструкциям из `Dockerfile`?

1. **База:** Сборка начинается с родительского образа (`FROM`), который предоставляет начальный набор слоев `lowerdir`.
2. **Создание новых слоев:** Каждая инструкция, изменяющая файловую систему (`RUN`, `COPY`, `ADD`), берет слои предыдущего шага в качестве `lowerdir`, выполняет операцию во временном изменяемом слое и сохраняет результат как **новый постоянный слой `lowerdir`**.
+
[NOTE]
Инструкции метаданных (`WORKDIR`, `ENV`, `EXPOSE`, `USER`, `CMD`) не создают новых файлов на диске, но фиксируют настройки окружения в конфигурации образа для всех последующих шагов.

3. **Линейная цепочка:** В итоге образ формируется как строгая последовательность слоев, где каждый шаг жестко опирается на все предыдущие шаги  --  на весь накопленный префикс.

=== Повторная сборка

Когда вы повторно запускаете `docker build`, Docker не выполняет все инструкции заново. Он идет по `Dockerfile` сверху вниз:

* Для каждого шага проверяется: существует ли уже на диске слой, полученный из *этого же базового состояния* точно *такой же командой* (в случае `COPY` & `ADD` также проверяется, не поменялись ли файлы)?
* Если такой слой найден, Docker не тратит ресурсы на повторный запуск команды, а **просто переиспользует уже готовый слой с диска**.
* Но если команда или копируемые файлы изменились, Docker выполняет шаг заново и создает новый слой с новым идентификатором. А поскольку все следующие команды должны накладываться поверх этого нового слоя, старые сохраненные слои для них уже не актуальны  --  Docker вынужден выполнить заново **все инструкции до самого конца файла**.

=== Кэширование сборки (Build Cache)

Вот это свойство автоматического переиспользования готовых слоев по совпадению шагов называют **кэшированием сборки (Build Cache)**:

* В выводе сборки шаги, для которых нашелся готовый слой, помечаются как **`CACHED`**.
* Важно понимать: кэшируется **строго неизменный префикс** инструкций вашего `Dockerfile`. Пока верхние строки не меняются, сборка проходит мгновенно. Но первое же изменение в середине файла сбрасывает кэш для всего оставшегося «хвоста» сборки.

=== Следствие: порядок инструкций

Понимая, что кэшируется именно неизменный префикс, становится очевидным главный принцип организации `Dockerfile`: **редко меняющиеся шаги должны идти как можно выше, а часто меняющиеся  --  как можно ниже**.

.Пример: влияние порядка команд на скорость сборки
[%collapsible]
====
*Неоптимальный порядок команд:*
[,bash]
----
# ПЛОХОЙ DOCKERFILE
FROM python:3.12-slim
WORKDIR /app

# Копируем весь проект целиком (включая часто меняющийся код)
COPY . .

# Устанавливаем зависимости
RUN pip install -r requirements.txt

CMD ["python", "main.py"]
----
Вы изменили всего одну строчку в коде приложения. Команда `COPY . .` видит изменение файлов и ломает префикс сборки. В результате шаг `RUN pip install` теряет возможность переиспользовать готовый слой и вынужден заново скачивать и компилировать все библиотеки, растягивая сборку на минуты.

*Оптимальный порядок команд:*
[,bash]
----
# ХОРОШИЙ DOCKERFILE
FROM python:3.12-slim
WORKDIR /app

# Копируем ТОЛЬКО манифест зависимостей, он меняется редко
COPY requirements.txt .

# Устанавливаем библиотеки
RUN pip install -r requirements.txt

# И только в самом конце копируем часто меняющийся код приложения
COPY . .

CMD ["python", "main.py"]
----
Теперь при любых правках в исходном коде шаги 1 и 2 остаются неизменным закэшированным префиксом. Docker мгновенно берет готовые слои, и заново собирается только финальный шаг копирования кода.
====

=== Очистка временных файлов и whiteout в слоях

Как мы выяснили в статье про OverlayFS, удаление файлов на новом шаге не освобождает место на диске, а лишь устанавливает whiteout-маркер в верхнем слое. Физически удаленные файлы продолжают лежать в нижних слоях образа.

Поэтому скачивание, распаковку и удаление временных архивов производят **строго в рамках одной инструкции `RUN`**:

[,bash]
----
# ПРАВИЛЬНО: архив удален в том же слое, где был скачан
RUN wget https://example.com/app.tar.gz \
 && tar -xzf app.tar.gz \
 && rm app.tar.gz
----

Если разбить эти действия на две отдельные команды `RUN`:

[,bash]
----
# ОШИБКА: архив навсегда останется в нижнем слое
RUN wget https://example.com/app.tar.gz && tar -xzf app.tar.gz
RUN rm app.tar.gz
----

Архив `app.tar.gz` навсегда останется в промежуточном слое: команда `rm` лишь скроет его whiteout-маркером, но он продолжит занимать место в итоговом образе.

== Инспекция слоев и альтернативы

=== Просмотр слоев: docker history

Чтобы увидеть получившуюся цепочку слоев любого образа, создавшие их инструкции `Dockerfile` и занимаемый ими размер на диске, используют команду `docker history`:

[,console]
----
$ docker history my-app:1.0
----

В выводе видно, какая именно инструкция сформировала каждый слой и сколько мегабайт он добавил к размеру образа.

=== Ручное создание слоев: docker commit

Исторически до появления `Dockerfile` образы собирали вручную: запускали контейнер, вводили команды в интерактивном терминале, а затем сохраняли текущий изменяемый слой (`upperdir`) в новый статический слой командой `docker commit`:

[,console]
----
$ docker commit <контейнер> my-new-image:v1
----

В промышленной разработке `docker commit` считается антипаттерном: полученный образ становится невоспроизводимым, его нельзя автоматически пересобрать при обновлениях, а в слой попадает мусор из сессии терминала.

Команду используют лишь в исключительных ситуациях  --  для быстрой локальной отладки или спасения данных из сломанного контейнера. Все рабочие образы собирают строго через `Dockerfile`.
