В прошлой статье мы поняли, что образ  --  это то, из чего создаётся файловая система контейнера, и запускали контейнеры из готовых образов вроде `alpine`. В этой статье разберем, как устроена файловая система контейнера изнутри.

== Зачем контейнерам слои: проблема масштабирования

=== Образ vs Контейнер

* **Образ (Image)**  --  неизменяемый (read-only) шаблон файловой системы, содержащий файлы операционной системы, системные утилиты, библиотеки и код приложения, а также метаданные (переменные окружения, порты по умолчанию).
* **Контейнер (Container)**  --  запущенный изолированный процесс, использующий файловую систему, развернутую из этого образа (её называют `rootfs`).

=== Экономия диска при запуске десятков копий

Если запустить 50 одинаковых контейнеров каждый весом ~100 МБ, наивный подход с полным копированием файлов для каждого экземпляра потребовал бы 5 ГБ дискового пространства и ощутимое время на копирование при каждом старте.

Вместо этого Docker использует послойную архитектуру хранения данных:

* Все 50 контейнеров используют *одни и те же* неизменяемые исходные файлы образа на диске.
* Каждый контейнер получает свой собственный изолированный слой для записи, который накладывается поверх образа. Изменения внутри одного контейнера не видны остальным и не могут повредить исходный образ.

Эту механику обеспечивает **OverlayFS**.

== Как устроена OverlayFS

=== Слои lowerdir, upperdir и точка монтирования merged

**OverlayFS**  --  это драйвер ядра Linux, который умеет брать несколько разных каталогов и объединять («накладывать») их друг на друга в одну итоговую папку:

1. **Нижние слои (`lowerdir`)**  --  неизменяемые каталоги, смонтированные строго в режиме только для чтения (read-only). Они накладываются друг на друга снизу вверх. Это файлы самого образа, который тоже состоит из слоёв. Подробнее обсудим в следующей статье.
2. **Верхний слой (`upperdir`)**  --  изменяемый каталог (read-write), который накладывается самым верхним слоем поверх получившегося набора слоев `lowerdir`. Для каждого запущенного контейнера создается свой собственный отдельный `upperdir`. Это пространство, куда контейнер вносит изменения по ходу своей работы.
3. **Объединенный корень (`merged`)**  --  итоговая виртуальная точка монтирования, собранная из слоев `lowerdir` и персонального `upperdir`. Именно ее процесс внутри конкретного контейнера видит как свой корень `/`.

== Поведение файлов: Copy-on-Write и Whiteout

=== Чтение и запись (Copy-on-Write)

* **Чтение:** если файл не менялся, он читается напрямую из нижних слоев образа (`lowerdir`). Если файл уже был изменен или создан внутри контейнера, чтение идет из `upperdir`.
* **Запись (Copy-on-Write):** при первой попытке изменить файл из образа ядро полностью копирует его в изменяемый слой `upperdir` конкретно этого контейнера и применяет правки уже там. Исходный файл в образе остается нетронутым. Все последующие правки этого файла пишутся напрямую в готовую копию в `upperdir`.

=== Удаление файлов и whiteout-маркеры

Удалить файл из read-only слоя `lowerdir` невозможно. Поэтому при удалении файла ядро создает в `upperdir` специальный файл-заглушку (**whiteout**). OverlayFS видит этот маркер и скрывает файл из точки монтирования `merged`. Внутри контейнера файл исчезает, но в нижних слоях образа продолжает физически занимать место.

[IMPORTANT]
При модификации файл копируется в `upperdir` целиком. Изменение одного байта в файле размером 500 МБ вызовет копирование всех 500 МБ в слой контейнера. Поэтому базы данных и часто меняющиеся файлы не хранят в слоях контейнера, а выносят в тома (Volumes)  --  их мы разберем позже.

== Инспекция слоя контейнера: docker diff

Чтобы увидеть, какие файлы появились или изменились в `upperdir` конкретного контейнера с момента его запуска, используют команду `docker diff`:

* `A` (Added)  --  новый файл, созданный в контейнере;
* `C` (Changed)  --  существующий файл образа скопирован по CoW и изменен;
* `D` (Deleted)  --  файл удален (в `upperdir` выставлен whiteout-маркер).

[,console]
----
$ docker diff my-container
C /etc
A /etc/my.conf
D /etc/hosts
----
