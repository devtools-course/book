= Запуск и жизненный цикл контейнеров
:page-authors: Михаил Агафонов
:description: Архитектура запуска Docker от CLI до runc, основные режимы docker run, проброс портов, переменные окружения и управление жизненным циклом контейнеров
:icons: font

Итак, в прошлом разделе мы поняли, какие проблемы решают контейнеры и что они представляют собой просто изолированный процесс. В этой статье обсудим, как работать с контейнерами при помощи `Docker`.

== Архитектура: как устроен запуск под капотом

Когда мы вводим команду в консоли, утилита `docker` сама по себе процесс не изолирует и контейнер не создает. Запуск  --  это цепочка взаимодействия нескольких компонентов:

**Docker CLI** (консольный клиент `docker`) отвечает за взаимодействие через консоль, она принимает и парсит команду, после чего отправляет запрос через сокет `/var/run/docker.sock`.  

**Docker Daemon (`dockerd`)** слушает сокет, принимает запрос, создаёт необходимые разделы на диске и виртуальные сети, настраивает маршрутизацию. После передаёт задачу `containerd`.

**Container Daemon (`containerd`)** централизованно управляет всеми контейнерами на хосте  --  создаёт, запускает, останавливает, следит за состоянием. Это происходит при помощи `runc`.

Низкоуровневая утилита **runc** непосредственно запускает контейнер, после того как `containerd` вызывает её. Именно она обращается к ядру Linux для запуска изолированного процесса. После этого она тут же завершает свою работу, оставляя контроль за контейнером `containerd`.

== Базовый синтаксис docker run

Перед тем, как запустить наш первый контейнер, разберёмся *из чего* мы будем его запускать. Мы уже поняли, что для контейнера создаётся его собственная файловая система. Она монтируется к определённой точке файловой системы хоста (обычно `/var/lib/docker/containers/<container-unique-id>`), куда и переносится корень при помощи `pivot_root` для изолируемого процесса. Чтобы наполнить эту изолированную файловую систему контейнера  --  она создаётся из заранее подготовленного фиксированного набора файлов  --  *образа (Image)*. По сути образ является просто шаблоном для развёртки файловых систем контейнеров. Далее мы ещё подробнее поговорим про образы, пока что можно относиться к контейнеру как к работающему экземпляру его образа.

[,console]
----
$ docker run [OPTIONS] IMAGE [COMMAND] [ARG...]
----

По умолчанию контейнер запускается прикреплённым к текущему терминалу, вывод и ошибки идут прямо в него, а остановить контейнер можно при помощи `Ctrl+C`.

Если не указать имя через флаг **`--name`**, Docker придумает случайное имя сам. В скриптах и реальных проектах лучше всегда задавать осмысленное имя: к контейнеру по имени удобно обращаться и связывать сервисы по сети.

== Режимы работы: фон или терминал

=== Фоновый режим (-d)

Чтобы контейнер работал в фоне, используют флаг `-d` (`--detach`):

[,console]
----
$ docker run -d --name my-web nginx:alpine
----

Это полезно, например, для запуска базы данных или веб-сервера.

=== Интерактивный режим (-it): TTY и потоки ввода-вывода

Когда вы хотите «зайти» внутрь контейнера и запускать команды внутри контейнера прямо из своего терминала, используют связку флагов `-it`:

[,console]
----
$ docker run --rm -it alpine sh
----

[NOTE]
====
Подробнее о том, что значит часть команды после названия образа мы поговорим немного позже. До тех пор можно считать, что это и есть процесс, изолируемый в контейнере. То есть мы просто запустили shell.
====

* **`-i` (`--interactive`)**  --  оставляет поток ввода в контейнер открытым, по умолчанию Docker закрывает STDIN. 
* **`-t` (`--tty`)**  --  включает режим эмуляции терминала: подсвечивает текст, обрабатывает нажатие стрелочек, `Ctrl+C`, `Tab`, цвета и т.д. 

Флаг `-t` нужен только тогда, когда за клавиатурой сидит живой человек. Если же вы скармливаете в контейнер файл или результат другой команды через пайп или вводите из файла, флаг `-t` использовать **нельзя**, вылезет ошибка `the input device is not a TTY`, т.к. передаваемый файл  --  не терминал, а `-t` ожидает прикрепление к терминалу.

В таких сценариях передают **только флаг `-i`**:

[,console]
----
$ echo "Hi!" | docker run --rm -i alpine cat # output: Hi! 
----

=== Запуск составных команд и конвейеров (sh -c)

Если написать так:

[,console]
----
$ docker run --rm alpine ls -la | wc -l
----

Конвейер `| wc -l` выполнится на вашем хосте, а не в контейнере! Чтобы пайплайн отработал целиком внутри контейнера, его нужно завернуть в шелл:

[,console]
----
$ docker run --rm alpine sh -c "ls -la | wc -l"
----

== Конфигурация окружения и сети

=== Переменные окружения (-e, --env-file) и рабочая папка (-w)

Передать конфигурацию в приложение можно через переменные окружения:

* Флаг `-e` передает одиночную переменную:
+
[,console]
----
$ docker run -d -e MODE=production -e PORT=8080 my-app
----

* Флаг `--env-file` загружает файл со списком переменных:
+
[,console]
----
$ docker run -d --env-file .env my-app
----

* Флаг `-w` (`--workdir`) меняет рабочую директорию, в которой стартует процесс:
+
[,console]
----
$ docker run --rm -w /var/log alpine pwd
/var/log
----

=== Проброс портов (-p, -P)

По умолчанию сеть контейнера изолирована от хоста. Чтобы открыть доступ к приложению снаружи, нужно пробросить порт:

[,console]
----
$ docker run -d -p 8080:80 nginx:alpine
----

Синтаксис: `порт_хоста:порт_контейнера`. Теперь при обращении на `localhost:8080` запрос уйдет на порт `80` внутри контейнера.

**Важный нюанс:**
Запись `-p 8080:80` открывает порт на всех сетевых интерфейсах хоста. Если у вашего сервера есть внешний белый IP, сервис станет доступен всему интернету.

Чтобы порт был доступен только локально на вашей машине, явно укажите IP-адрес:

[,console]
----
$ docker run -d -p 127.0.0.1:8080:80 nginx:alpine
----

Флаг **`-P` (заглавная)** открывает все порты, описанные в `Dockerfile` (скоро поговорим и о нём) на случайных свободных портах хоста. Узнать, какой порт выделился, можно командой `docker port <имя_контейнера>`.

== Жизненный цикл и управление

=== Статусы контейнера, docker start и флаг --rm

Важно понимать:

* *`docker run`* *всегда создает совершенно новый контейнер* из образа.

* Когда процесс внутри контейнера завершает свою работу, контейнер не удаляется автоматически, а переходит в статус остановленного (`Exited`).

Все измененные в exited-контейнере файлы и логи продолжают храниться на диске. Вывести список всех (running & exited) контейнеров можно командой `docker ps -a` и **запустить заново** командой:

[,console]
----
$ docker start <имя_или_id>
----
При этом контейнер возобновит работу в том же состоянии, что и завершился. Окончательно удалить остановленный контейнер можно командой `docker rm <имя_или_id>`.

Если же контейнер нужен **разово**, то накапливать такие отработавшие контейнеры нет смысла. Для таких задач используют флаг **`--rm`**:

[,console]
----
$ docker run --rm IMAGE echo "Hello World"
----

Флаг `--rm` указывает Docker: как только процесс завершится, не переводи контейнер в статус `Exited`, а **удали его**.

=== Политики автоматического перезапуска (--restart)

Чтобы фоновые сервисы сами поднимались при сбоях или после перезагрузки хоста:

* `no`  --  не перезапускать (по умолчанию).
* `on-failure`  --  перезапускать только при аварийном падении (ненулевой код выхода).
* `always`  --  перезапускать всегда (даже если вы остановили его через `docker stop`, после перезагрузки сервера Docker поднимет его снова).
* `unless-stopped`  --  как `always`, но уважает ручную остановку: если вы сами ввели `docker stop`, после перезагрузки сервера он останется выключенным.

=== Повседневные команды: ps, logs, stop, exec

Повседневные команды для контроля запущенных сервисов:

* `docker ps`  --  показать работающие контейнеры.
* `docker ps -a`  --  показать все контейнеры, включая остановленные.
* `docker logs <имя>`  --  посмотреть вывод контейнера. Флаг `-f` позволяет следить за логами в реальном времени, а `--tail 50` покажет последние 50 строк.
* `docker stop <имя>`  --  посылает сигнал процессу `SIGTERM`, давая ему 10 секунд на корректное завершение. Если процесс не завершился, посылает `SIGKILL`.
* `docker kill <имя>`  --  сразу жестко убивает процесс сигналом `SIGKILL`.
* `docker exec -it <имя> sh`  --  подключается к уже работающему контейнеру и запускает в нем новый процесс (например, шелл для отладки).

=== Проблема PID 1 и корректная остановка (--init)

Команда `docker stop` отправляет процессу сигнал `SIGTERM`, ждет 10 секунд и, если процесс не завершился, принудительно убивает его сигналом `SIGKILL`.

Частая проблема: приложение не завершается само и всегда ждет таймаута в 10 секунд. Причина в поведении ядра Linux: **процесс с `PID 1` игнорирует `SIGTERM` по умолчанию**, если в коде программы явно не зарегистрирован обработчик этого сигнала.

Решения:

* Обрабатывать `SIGTERM` в коде приложения.
* Либо запускать контейнер с флагом **`--init`** (`docker run -d --init ...`): Docker запустит крошечный init-процесс, который займет `PID 1`, корректно перешлет `SIGTERM` вашему приложению.
