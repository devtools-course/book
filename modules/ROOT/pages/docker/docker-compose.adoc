= Мультиконтейнерные стенды (Docker Compose)
:page-authors: Михаил Агафонов
:description: Декларативное описание многоконтейнерных стендов в docker-compose.yaml, автоматическая сеть проекта, переменные окружения (.env и env_file), порядок запуска через depends_on и healthcheck
:icons: font

Реальное приложение редко состоит из одного изолированного контейнера: чаще всего требуется запустить целый комплекс (стенд) из множества компонентов, которые должны работать и взаимодействовать вместе.

Поднимать крупный стенд вручную крайне долго и неудобно: приходится по очереди выполнять десятки команд `docker run` с длинным набором флагов, вручную создавать общие сети и тома, а также строго соблюдать очерёдность запуска сервисов.

При последовательном запуске через `docker run` мы действуем **императивно**  --  то есть вручную задаём пошаговый алгоритм действий терминалу и сами контролируем каждый шаг.

**Docker Compose** предлагает **декларативный** подход. В едином конфигурационном файле мы описываем желаемое итоговое состояние системы: список сервисов, их зависимости, порты, переменные окружения и тома данных. После этого весь стенд запускается одной командой `docker compose up`  --  утилита сама обращается к демону Docker (`dockerd`), подготавливает окружение и поднимает все контейнеры в правильном порядке.

== Назначение и структура файла

Файл конфигурации определяет, как именно должен быть устроен и запущен ваш стенд.

=== Именование и поиск файла

В разных проектах можно встретить разные имена файла конфигурации. Это связано с эволюцией Compose:

* **`docker-compose.yaml` (и `.yml`)**  --  историческое и самое распространённое на практике имя. Большинство существующих проектов, статей и обучающих материалов используют именно его.
* **`compose.yaml` (и `.yml`)**  --  актуальный современный стандарт, принятый открытой спецификацией Compose Specification. Именно это имя официально рекомендует документация Docker.

При запуске команд утилита `docker compose` автоматически ищет конфигурационный файл в текущей папке по строгому приоритету:

1. `compose.yaml` (рекомендуемый современный стандарт)
2. `compose.yml`
3. `docker-compose.yaml` (наиболее привычный на практике)
4. `docker-compose.yml` (классическое историческое название)

Если файл назван нестандартно или находится в другой папке, путь к нему можно передать явно через флаг `-f` (например, `docker compose -f deploy.yaml up`).

=== Ключевые разделы: services, networks, volumes

Структура файла строится вокруг трёх основных разделов верхнего уровня:

* **Сервисы (`services:`)**  --  главный и обязательный раздел. Каждый сервис описывает отдельный компонент приложения и правила его запуска в виде контейнера:
** **Образ контейнера:** сервис может использовать уже готовый образ (`image:`)  --  тогда Compose ищет его локально или скачивает из реестра (например, Docker Hub), либо собираться из локального `Dockerfile` (`build: .`).
** **Параметры запуска:** конфигурация окружения, сети и ресурсов контейнера (переменные окружения `environment:`, публикация портов `ports:`, правила перезапуска `restart:`, точки монтирования).
* **Сети (`networks:`)**  --  раздел для настройки сетевого взаимодействия между контейнерами. По умолчанию Compose автоматически создаёт для проекта изолированную bridge-сеть и подключает к ней все сервисы; внутри неё контейнеры доступны по именам своих сервисов благодаря встроенному Docker DNS. Явно описывать секцию `networks:` нужно только в сложных проектах, когда разные сервисы требуется изолировать друг от друга.
* **Тома (`volumes:`)**  --  раздел для объявления именованных томов, хранением и жизненным циклом которых управляет сам Docker. Данные в таких томах сохраняются при перезапуске и пересоздании контейнеров.

[NOTE]
====
В старых руководствах в начале файла часто встречается строка `version: "3.8"`, а запуск производился отдельной утилитой `docker-compose` (через дефис). В современном Docker используется встроенный плагин `docker compose` (через пробел), а директиву `version:` указывать больше не требуется  --  формат файлов стандартизирован спецификацией Compose Specification.
====

== Базовый пример: docker-compose.yaml

Конфигурационные файлы Compose пишутся на языке **YAML** (`.yaml` или `.yml`). Его синтаксис опирается на три базовых правила:

* **Пары «ключ: значение»:** разделяются двоеточием с обязательным пробелом после него (`key: value`).
* **Вложенность (иерархия):** задаётся отступами из пробелов (обычно 2 пробела на уровень). Символ табуляции (`\t`) использовать запрещено  --  парсер выдаст синтаксическую ошибку.
* **Списки:** элементы списка начинаются с дефиса с пробелом (`- item`).

[NOTE]
====
У формата YAML есть важная особенность: он пытается автоматически определять типы данных. Из-за этого строки без кавычек могут неожиданно преобразоваться:

* Значения `yes`, `no`, `on`, `off` парсер автоматически превратит в логические `true` / `false`.
* Запись вида `80:22` парсер может интерпретировать как число в шестидесятеричной системе счисления.

Поэтому строки, спецсимволы и составные идентификаторы в YAML всегда рекомендуется явно оборачивать в кавычки.
====

Посмотрим на типовой стенд из веб-приложения и базы данных PostgreSQL:

[,yaml]
----
services:
  # Сервис нашего приложения
  web:
    build: .                          # Собираем образ из Dockerfile в текущей папке
    ports:
      - "127.0.0.1:8080:8080"         # Доступен только локально на хосте, без выхода во внешнюю сеть
    environment:
      DB_HOST: db                     # Обращаемся к базе по имени соседнего сервиса
      DB_NAME: shop
      DB_PASSWORD: secretpassword
    restart: unless-stopped

  # Сервис базы данных
  db:
    image: postgres:16-alpine         # Используем готовый официальный образ
    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: secretpassword
    volumes:
      - pg_data:/var/lib/postgresql/data  # Подключаем именованный том для сохранения данных

# Объявление именованных томов уровня проекта
volumes:
  pg_data:
----

Обратите внимание на ключевые особенности этого файла:

1. **Взаимодействие по имени сервиса:** сервису `web` не нужно знать IP-адрес базы данных. Он просто обращается к хосту `db`  --  встроенный Docker DNS внутри проектной сети сам связывает это имя с контейнером базы.
2. **Как работают порты между контейнерами:** внутри общей bridge-сети контейнеры видят любые порты друг друга напрямую без дополнительных настроек. Сервис `web` подключается к базе по её штатному порту `db:5432`. Секция `ports:` нужна **только** для проброса порта наружу  --  на ваш физический компьютер. Базе данных доступ извне не требуется (к ней обращается только приложение), поэтому у сервиса `db` секции `ports:` нет вовсе  --  она надёжно изолирована от внешней сети.
3. **Безопасная публикация порта (`127.0.0.1:8080:8080`):** если указать просто `"8080:8080"`, Docker откроет порт на всех сетевых интерфейсах хоста (`0.0.0.0`), и приложение станет доступно из внешней сети. Привязка к `127.0.0.1` гарантирует, что сервис доступен только локально с вашего хоста, а не извне.
4. **Именование томов и изоляция проектов:** по умолчанию Compose использует в качестве имени проекта имя текущей папки и добавляет его префиксом к ресурсам (например, `myapp_pg_data`), предотвращая конфликты с другими проектами. Если папки в разных местах файловой системы называются одинаково, имя проекта можно явно задать директивой `name: myproject` в начале файла или флагом `docker compose -p myproject up`.

== Порядок запуска: depends_on и healthcheck

По умолчанию Docker Compose запускает все описанные сервисы одновременно и параллельно. Если одному сервису для работы требуется другой, порядок их старта можно задать директивой `depends_on`: она указывает, какой сервис Compose должен запустить раньше.

Однако простого указания `depends_on` недостаточно:

[,yaml]
----
services:
  web:
    build: .
    depends_on:
      - db
  db:
    image: postgres:16-alpine
----

В таком виде `depends_on` ждёт только момента, когда ядро запустит главный процесс контейнера `db` (PID 1). Но процессу базы данных после старта самого процесса требуется время на инициализацию. Если приложение стартует раньше, оно попытается подключиться к базе, получит ошибку `Connection refused` и аварийно завершится.

Решается эта проблема связкой `depends_on` с условием `condition: service_healthy` и механизмом **Healthcheck**, который мы изучали в предыдущей статье:

[,yaml]
----
services:
  web:
    build: .
    depends_on:
      db:
        condition: service_healthy    # Ждём именно готовности базы, а не просто старта процесса

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: shop
      POSTGRES_PASSWORD: secretpassword
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d shop || exit 1"]
      interval: 3s
      timeout: 3s
      retries: 5
----

Теперь Compose сначала запустит `db`, дождётся, пока проверка `pg_isready` вернёт успешный код `0` (статус `healthy`), и только после этого начнёт запуск контейнера `web`.

[NOTE]
Директива `depends_on` управляет только порядком первичного запуска стенда. Если база данных перезапустится уже во время работы, приложение должно уметь переподключаться к ней самостоятельно.

== Переменные окружения: .env, environment и env_file

Хранить пароли и настройки прямо в `docker-compose.yaml` неудобно и небезопасно: секреты и изменяемые параметры принято выносить отдельно. Для гибкой настройки параметров Compose предоставляет два разных механизма, решающих разные задачи:

=== Подстановка переменных из файла .env

Если в папке рядом с `docker-compose.yaml` находится файл `.env`:

[,text]
----
APP_PORT=8080
POSTGRES_PASSWORD=supersecret
----

Compose автоматически считывает его и подставляет значения вместо переменных вида `$\{ИМЯ_ПЕРЕМЕННОЙ}` внутри YAML-файла (через `:-` можно указать запасное значение по умолчанию):

[,yaml]
----
services:
  web:
    ports:
      - "127.0.0.1:${APP_PORT:-8080}:8080"
    environment:
      DB_PASSWORD: ${POSTGRES_PASSWORD}
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
----

[IMPORTANT]
Файл `.env` используется **только для подстановки значений в сам YAML-файл**  --  внутрь контейнеров эти переменные автоматически не попадают. Чтобы приложение увидело переменную, её нужно явно передать через секцию `environment:` или `env_file:`.

=== Передача переменных в контейнер (environment и env_file)

* **`environment:`**  --  перечисляет переменные списком прямо в файле конфигурации. Это удобно для общих настроек приложения.
* **`env_file:`**  --  загружает готовый файл со списком `КЛЮЧ=ЗНАЧЕНИЕ` напрямую в окружение контейнера (аналог флага `docker run --env-file`):
+
[,yaml]
----
services:
  web:
    build: .
    env_file:
      - .env.app
----

Проверить, какой итоговый файл конфигурации получился после всех подстановок из `.env`, можно командой `docker compose config`.

== Управление стендом

Утилита Docker Compose, ровно как и стандартный Docker CLI,  --  это просто надстройка (клиент) над демоном Docker (`dockerd`). Что один инструмент, что другой создаёт абсолютно одинаковые контейнеры, сети и тома. Единственное отличие состоит в том, что Compose автоматически добавляет к именам созданных объектов префикс проекта и номер экземпляра (например, `myapp-web-1` и `myapp-db-1`).

Поэтому любые контейнеры, запущенные через Docker Compose, можно в любой момент обслуживать с помощью стандартных команд `docker`, которые мы изучали ранее: просматривать через `docker ps`, читать их логи через `docker logs`, подключаться через `docker exec` или останавливать через `docker stop`.

Преимущество же команд `docker compose` в том, что они управляют **всеми компонентами стенда целиком** и оперируют короткими логическими именами сервисов (`web`, `db`):

* **`docker compose up`**  --  создаёт и запускает все ресурсы стенда в интерактивном режиме (на переднем плане). В терминал выводится объединённый цветной поток логов от всех сервисов, а нажатие `Ctrl+C` корректно останавливает весь стенд.
* **`docker compose up -d`**  --  запускает стенд в фоновом режиме (`-d` от *detached*), сразу возвращая управление в терминал. Контейнеры продолжают работать в фоне. Команда обладает свойством **идемпотентности**: при повторном запуске она не перезапускает работающие контейнеры, а пересоздаёт только те, конфигурация которых в файле изменилась.
* **`docker compose up -d --build`**  --  принудительно пересобирает образы перед запуском для сервисов с директивой `build:`. Обычный `up -d` собирает локальный образ из `Dockerfile` только один раз при первом старте; если вы внесли изменения в исходный код приложения, без флага `--build` Compose запустит ранее собранный образ и не заметит изменений. Для сервисов с директивой `image:` флаг `--build` сборку не вызывает (у них нет `Dockerfile`).
* **`docker compose ps`**  --  показывает статус всех сервисов проекта, проброшенные порты и состояние проверок здоровья (`healthy`/`unhealthy`).
* **`docker compose logs -f web`**  --  выводит логи конкретного сервиса в реальном времени (если опустить имя сервиса, выводится общий поток логов всех компонентов стенда).
* **`docker compose stop`**  --  останавливает контейнеры стенда без их удаления.
* **`docker compose down`**  --  останавливает и полностью удаляет контейнеры и сеть проекта, но **сохраняет именованные тома** (данные базы данных остаются нетронутыми).

[WARNING]
Команда `docker compose down -v` (или `--volumes`) удаляет не только контейнеры, но и **все связанные именованные тома**. Используйте этот флаг осторожно, только когда требуется начисто стереть все накопленные данные.

=== Запуск команд: exec против run

Для запуска команд внутри окружения сервисов в Compose есть две команды с принципиально разным назначением:

* **`docker compose exec`**  --  подключается к **уже запущенному и работающему** контейнеру (аналог `docker exec`). Обычно применяется для отладки или открытия командной оболочки внутри работающего сервиса:
+
[,console]
----
$ docker compose exec web sh
----
* **`docker compose run --rm`**  --  запускает **новый временный контейнер** сервиса в сети проекта для выполнения разовой задачи (например, прогона тестов или скриптов) и сразу удаляет его после завершения. Основной работающий стенд при этом не затрагивается:
+
[,console]
----
$ docker compose run --rm web npm test
----
