= Тома и хранение данных
:page-authors: Михаил Агафонов
:description: Как сохранять данные вне контейнера: работа маунтов в обход OverlayFS, bind mounts, named volumes, tmpfs, права UID:GID и проброс docker.sock
:icons: font

Из статьи про OverlayFS мы знаем, что все изменения внутри запущенного контейнера пишутся в его собственный слой `upperdir`. Стоит удалить контейнер через `docker rm`  --  и эти данные пропадут. В этой статье разберем, как хранить данные независимо от жизни контейнера и обмениваться файлами с хостом.

== Зачем выносить данные из контейнера

Есть три причины не держать рабочие данные внутри слоя контейнера:

* **Сохранность данных:** контейнеры задуманы как заменяемые. Чтобы обновить PostgreSQL на новую версию, старый контейнер удаляют и поднимают новый из свежего образа  --  данные БД должны пережить эту замену.
* **Производительность:** при записи в существующий файл внутри `OverlayFS` срабатывает Copy-on-Write (файл копируется в `upperdir` целиком). Для баз данных с постоянной случайной записью на диск это приведёт к лишним копированиям.
* **Обмен файлами:** часто нужно передать в контейнер конфиги, исходный код с хоста или расшарить одну директорию между двумя контейнерами.

== Механизм монтирования под капотом

Монтирование в Docker  --  это стандартный механизм `mount` ядра Linux внутри `mnt`-неймспейса контейнера (неймспейсы обсуждались в первой статье). Docker просто перекрывает выбранный путь внутри файловой системы контейнера (`merged`) директорией с хоста или областью оперативной памяти **в обход OverlayFS**.

Отсюда сразу следуют три свойства:

* Чтение и запись идут напрямую в файловую систему хоста без потерь на Copy-on-Write.
* Данные живут независимо от контейнера и не удаляются при `docker rm`.
* Если примонтировать каталог хоста поверх непустой папки образа, файлы образа в этой папке окажутся скрыты, пока маунт активен. Это стандартное поведение `mount` в Linux.

В зависимости от того, *где* лежат данные и *кто* ими управляет, выделяют три механизма: **Bind Mounts**, **Named Volumes** и **`tmpfs`**.

== Bind Mounts: проброс путей с хоста

Bind Mount напрямую связывает конкретную директорию или отдельный файл с файловой системы вашей машины с путем внутри контейнера. Для этого в команде `docker run` чаще всего используют флаг `-v` (сокращение от `--volume`). Синтаксис флага связывает два пути через двоеточие: `-v <путь_на_хосте>:<путь_в_контейнере>` (кроме `-v`, для этого можно использовать более явный флаг `--mount`, который мы сравним далее).

[,console]
----
$ docker run -d -v /path/on/host:/path/in/container my-app
----

Например, для проброса папки `src` из текущей директории хоста можно выполнить `docker run -d -v "$(pwd)/src:/app/src" my-app`. Изменения файлов в этой папке на хосте мгновенно отобразятся внутри контейнера  --  это удобно для локальной разработки, так как не требует пересборки образа при каждом изменении кода.

Если контейнер должен только *читать* файлы (например, конфигурацию или сертификаты), в конец записи маунта добавляют опцию `:ro` (монтирование в режиме read-only):

[,console]
----
$ docker run -d -v /path/on/host/nginx.conf:/etc/nginx/nginx.conf:ro nginx:alpine
----

=== Права доступа и пользователи

При работе с Bind Mount важно понимать, от чьего имени файловая система хоста выполняет операции. 

Ядро Linux не знает имен пользователей внутри контейнера  --  оно проверяет права исключительно по числовым **`UID:GID`**:

* **Проблема `root:root`:** по умолчанию процесс в контейнере работает с UID 0 (root). Все созданные им файлы на хосте тоже получат владельца `root:root`, и редактировать или удалить их без `sudo` не получится.
* **Решение (`--user`):** при запуске контейнера можно передать свой UID и GID:
+
[.wrap,console]
----
$ docker run --rm --user "$(id -u):$(id -g)" -v /path/on/host:/app alpine touch /app/test.txt
----
+
Файл `test.txt` создастся на хосте с вашими правами.

Конфликт UID  --  главная причина, почему для баз данных (PostgreSQL, MySQL) не используют Bind Mounts. Демон базы в контейнере работает от своего пользователя (например, `postgres` с UID 999). Если примонтировать обычную папку хоста через Bind Mount, база упадет с ошибкой `Permission denied`, пока вы вручную не сделаете `chown -R 999` на хосте. Именованные тома (Named Volumes) избавляют от этой проблемы: Docker сам создает каталог и настраивает права для сервиса.

=== Одиночные файлы и потеря связи по inode

Примонтировать через Bind Mount можно не только каталог, но и отдельный файл. Однако при монтировании конкретного файла ядро Linux привязывается к его номеру **`inode`**, а не к пути в дереве файловой системы.

Большинство редакторов кода (VS Code, Vim, Nano, JetBrains) ради безопасности сохраняют файлы не перезаписью байтов на месте, а атомарно: создают временный файл с новым содержимым (с новым `inode`) и подменяют оригинал системным вызовом `rename()`.

В результате на хосте по старому пути появляется файл с новым `inode`, а точка монтирования внутри контейнера продолжает указывать на старый `inode`  --  и правки в контейнере просто не появляются. Поэтому, если требуется обновлять конфиги на лету, лучше монтировать не единичный файл, а всю родительскую директорию целиком.

== Именованные тома (Named Volumes)

В отличие от Bind Mount, где вы сами выбираете путь на хосте, **именованный том (Named Volume)**  --  это постоянное хранилище, которым полностью управляет сам Docker. Вы задаете только понятное имя тома (например, `pg_data`), а демон Docker сам создает под него изолированную директорию на диске хоста (в `/var/lib/docker/volumes/<имя>/_data`) и настраивает права доступа.

Это стандартный и рекомендуемый способ хранения постоянных данных (например, баз данных): данные изолированы от прямого вмешательства с хоста, а жизненным циклом тома удобно управлять через CLI:

[,console]
----
$ docker volume create pg_data
$ docker volume ls
$ docker volume rm pg_data
$ docker volume prune # удалить все неиспользуемые тома
----

Подключение тома к контейнеру (если тома еще нет, Docker создаст его автоматически при старте):

[,console]
----
$ docker run -d -v pg_data:/var/lib/postgresql/data postgres:alpine
----

Обратите внимание на синтаксис флага `-v`: если до двоеточия указан путь на диске (начинается с `/` или `./`), Docker выполняет Bind Mount; если передано просто имя (`pg_data`)  --  подключает том. Если имя опустить вовсе (например, `-v /var/lib/postgresql/data`), Docker создаст *анонимный том* со случайным длинным хэшем вместо имени, но на практике всегда задают явные имена.

[NOTE]
У томов есть важное отличие от Bind Mount: если примонтировать **новый пустой том** в папку контейнера, где в образе уже лежали начальные файлы, Docker автоматически скопирует их внутрь этого тома. При Bind Mount исходные файлы образа в точке монтирования просто скрываются.

== tmpfs: монтирование в оперативную память

Иногда данные вообще не должны попадать на физический диск  --  например, при работе с секретами (API-ключами, токенами) или когда сервису нужен максимально быстрый временный кэш.

Для таких задач используют **`tmpfs`**  --  монтирование области оперативной памяти хоста (RAM) напрямую в директорию контейнера:

[,console]
----
$ docker run -d --tmpfs /tmp/secrets my-app
----

Данные в таком каталоге существуют только в оперативной памяти и бесследно исчезают сразу после остановки контейнера.

== Синтаксис: -v против --mount

Кроме коротких флагов `-v` и `--tmpfs`, в Docker есть универсальный флаг `--mount`. Он настраивается через пары `ключ=значение`, разделенные запятыми:

* **`type`**  --  тип монтирования: `bind`, `volume` или `tmpfs`.
* **`source`** (или `src`)  --  источник данных: путь на хосте для `bind` или имя тома для `volume` (для `tmpfs` опускается).
* **`target`** (или `dst`)  --  абсолютный путь внутри контейнера, куда монтируются данные.
* **Дополнительные опции:** например, `readonly` для монтирования в режиме только для чтения.

Примеры использования:

[.wrap,console]
----
# Именованный том
$ docker run -d --mount type=volume,source=pg_data,target=/var/lib/postgresql/data postgres:alpine

# Bind Mount в режиме только для чтения
$ docker run -d --mount type=bind,source="$(pwd)/src",target=/app/src,readonly my-app

# Монтирование в оперативную память
$ docker run -d --mount type=tmpfs,target=/tmp/secrets my-app
----

Флаг `--mount` многословнее, но гораздо безопаснее в скриптах и продакшене:

. Он самодокументирован: по параметрам сразу видно, где источник, где назначение и какой тип хранилища выбран.
. Он защищает от опечаток: если при `-v /wrong/path:/app` Docker молча создаст на хосте новую пустую папку `/wrong/path` с правами `root`, то `--mount type=bind` при отсутствии указанного пути сразу завершится с понятной ошибкой.

== Проброс сокета Docker

Поскольку в Linux сокет  --  это тоже файл, через Bind Mount внутрь контейнера можно пробросить Unix-сокет демона Docker:

[.wrap,console]
----
$ docker run --rm -v /var/run/docker.sock:/var/run/docker.sock docker:cli docker ps
----

Через этот сокет клиент внутри контейнера связывается напрямую с демоном хоста и может управлять соседними контейнерами на машине. Этот подход называют **DooD (Docker-outside-of-Docker)**. Он часто применяется в CI/CD, но фактически дает контейнеру полные права root на хосте.

Подробнее архитектуру DooD, сценарии применения и риски безопасности мы разберем в отдельной статье.
