== Системные компиляторы и утилиты

В системе есть несколько имён, которые легко перепутать:

`cc`::
Исторически «C compiler». Сегодня это симлинк на компилятор C по умолчанию: на Linux обычно на `gcc`, на macOS на `clang`. Многие Makefile по традиции зовут именно `cc`.

`c++`::
То же самое для C++, симлинк на `g++` или `clang++`.

`cpp`::
**Препроцессор C**, а не компилятор C++. Одно из самых неудачных совпадений имён в Unix. Запускается как `cpp file.c` и делает ровно то же, что `gcc -E`.

`gcc`, `g++`::
Компиляторы GNU напрямую.

`clang`, `clang++`::
Компиляторы LLVM. Флаги в основном совместимы с gcc, диагностика обычно понятнее.

Проверить, что стоит за именем:

[,console]
----
$ which cc && readlink -f "$(which cc)"
$ cc --version
----

=== gcc на macOS

К сожалению, macOS - вещь со своими тараканами в голове.

[,console]
----
$ gcc --version
Apple clang version 15.0.0 (clang-1500.3.9.4)
Target: arm64-apple-darwin23.5.0
----

На самом деле, на macOS `gcc` это *не gcc*. Это симлинк-заглушка на Apple Clang, оставленная для совместимости со скриптами сборки. Настоящего GNU-компилятора в системе нет, Xcode Command Line Tools ставят clang.

Практические последствия:

* Специфичные для GNU расширения и флаги могут не работать.
* Версия в выводе (`15.0.0`) это версия Apple Clang, а не gcc. Сравнивать её с версиями GNU бессмысленно.
* Динамические библиотеки называются `.dylib`, а не `.so`, формат Mach-O, а не ELF.
* Вместо `ldd` работает `otool -L`, вместо `LD_LIBRARY_PATH` - `DYLD_LIBRARY_PATH`, вместо `readelf` - `otool` и `nm`.
* `-rpath` есть и работает, но `$ORIGIN` называется `@loader_path`.

Настоящий gcc на macOS ставится через Homebrew и живёт под версионированным именем, чтобы не конфликтовать с заглушкой:

[,console]
----
$ brew install gcc
$ gcc-14 --version         <1>
x86_64-apple-darwin ... (Homebrew GCC 14.1.0)
----
<1> Именно `gcc-14`, а не `gcc`: последнее по-прежнему указывает на clang.
