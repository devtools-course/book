== Шаг 4. Линковка

Линковщик впервые видит проект целиком. Его работа:

. Собрать все объектные файлы и библиотеки в один образ.
. Разложить секции: все `.text` из всех объектников подряд, все `.data` подряд и так далее.
. Присвоить всему окончательные адреса.
. Пройтись по релокациям и подставить настоящие адреса вместо дырок.
. Убедиться, что каждый символ с классом `U` где-нибудь определён.

Если последнее не выполняется, получаем самую узнаваемую ошибку C++:

[,text]
----
/usr/bin/ld: main.o: in function 'main':
main.cpp:(.text+0x1f): undefined reference to 'print(char const*)'
collect2: error: ld returned 1 exit status
----

Читается она так: символ используется, но никто его не определил. Причины по убыванию частоты:

* Забыли передать линковщику `.cpp` или `.o`, где лежит определение.
* Забыли `-l` для библиотеки.
* Объявили функцию в заголовке, а реализацию не написали.
* Несовпадение сигнатур: объявили `print(const char*)`, а определили `print(char*)`. Символы разные, компилятор молчит, линковщик ругается.
* Забыли `extern "C"` при вызове C-библиотеки из C++ (или, наоборот, поставили лишний).

Зеркальная ошибка `multiple definition` означает обратное: символ определён дважды. Про неё говорили в разделе xref:compilation/symbols.adoc[Symbols & linkage].

TIP: Первое, что стоит сделать при `undefined reference`, - прогнать сообщение через `c++filt` и найти символ через `nm`. Обычно сразу видно, что сигнатура отличается на `const` или что объектник вообще не попал в команду линковки.

=== `ld` и порядок аргументов

`ld` это и есть линковщик. Напрямую его почти никогда не зовут: правильно звать через `gcc`, потому что драйвер сам добавит стартовый код (`crt1.o` и компанию) и системные библиотеки. Передать флаг именно линковщику можно через `-Wl,`:

[,console]
----
$ g++ main.o -Wl,--verbose            <1>
$ g++ main.o -Wl,-rpath,/opt/lib      <2>
----
<1> Всё после `-Wl,` уходит линковщику как есть.
<2> Запятые внутри превращаются в пробелы, то есть это `-rpath /opt/lib`.

Теперь про грабли, на которые наступают все.

CAUTION: **Порядок файлов и библиотек в команде линковки важен.** Линковщик идёт по аргументам слева направо и держит список ещё не разрешённых символов. Встретив статическую библиотеку, он вытаскивает из неё только те объектники, которые закрывают *уже накопленные* неразрешённые символы, и идёт дальше. Если библиотека указана раньше, чем тот, кто ей пользуется, на момент её просмотра нужных символов в списке ещё нет, и из библиотеки не возьмётся ничего.

[,console]
----
$ g++ -lmylib main.o -o app     <1>
$ g++ main.o -lmylib -o app     <2>
----
<1> Скорее всего `undefined reference`, хотя библиотека указана.
<2> Правильно: сначала тот, кто использует, потом то, что используется.

Если библиотеки ссылаются друг на друга по кругу, помогает группа:

[,console]
----
$ g++ main.o -Wl,--start-group -la -lb -Wl,--end-group -o app
----

Она заставляет линковщик крутить перечисленные библиотеки по кругу, пока символы продолжают разрешаться.

=== Статическая и динамическая линковка

Это развилка, от которой зависит почти всё дальнейшее.

Статическая линковка::
Код библиотеки физически копируется в исполняемый файл. Бинарь получается большим и самодостаточным: его можно унести на другую машину, и он запустится. Обновление библиотеки требует пересборки программы.

Динамическая линковка::
В бинарь кладётся только *запись о зависимости*: «мне нужна `libfoo.so.1`». Настоящий код подгружается при запуске программы динамическим загрузчиком. Бинарь маленький, библиотека одна на всех программы в системе и обновляется отдельно. Зато программа не запустится, если библиотеки на машине нет или версия не та.

По умолчанию gcc линкует динамически. Заставить статически:

[,console]
----
$ g++ -static main.cpp -o app          <1>
$ g++ -static-libstdc++ main.cpp       <2>
----
<1> Всё статически, включая libc. Бинарь будет мегабайтами.
<2> Только стандартная библиотека C++ статически, остальное динамически. Частый компромисс, когда программу надо запускать на машинах со старым gcc.

Посмотреть разницу:

[,console]
----
$ g++ main.cpp -o dyn && ls -lh dyn
-rwxr-xr-x 1 user user 17K dyn

$ g++ -static main.cpp -o st && ls -lh st
-rwxr-xr-x 1 user user 2.3M st

$ file dyn
dyn: ELF 64-bit LSB pie executable, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2
$ file st
st: ELF 64-bit LSB executable, statically linked
----

Строчка `interpreter /lib64/ld-linux-x86-64.so.2` это и есть динамический загрузчик: ядро запускает сначала его, а он уже находит и подгружает библиотеки, после чего передаёт управление в `main`.
