== Разбор: взаимные включения и почему порядок строк ломает сборку

Этот пример однажды сломал даже меня. Пусть есть два заголовка, каждый со стражем, и они включают друг друга.

[,cpp]
----
// a.h
#pragma once
#include "b.h"

struct A {
    B b;        // нужен ПОЛНЫЙ тип B
};
----

[,cpp]
----
// b.h
#pragma once
#include "a.h"

struct B {
    int x;      // про A ничего не знает
};
----

Теперь `main.cpp`, и вся интрига в порядке двух строк.

=== Вариант 1: сначала `a.h`

[,cpp]
----
#include "a.h"
#include "b.h"

int main() { A a; return a.b.x; }
----

Проследим за препроцессором по шагам:

. Встретили `#include "a.h"`, открыли `a.h`.
. `#pragma once` для `a.h` - отметили `a.h` как обработанный.
. Внутри `a.h` встретили `#include "b.h"`, открыли `b.h`.
. `#pragma once` для `b.h` - отметили.
. Внутри `b.h` встретили `#include "a.h"`. Файл уже отмечен, **разворачивается в пустоту**.
. Тело `b.h`: `struct B { int x; };`. Всё в порядке, `B` определён.
. Вернулись в `a.h`, продолжаем его тело: `struct A { B b; };`. Тип `B` уже известен и полон. Всё в порядке.
. `#include "b.h"` в `main.cpp` разворачивается в пустоту, файл уже обработан.

Итог единицы трансляции:

[,cpp]
----
struct B { int x; };
struct A { B b; };
int main() { A a; return a.b.x; }
----

Собирается.

=== Вариант 2: меняем строки местами

[,cpp]
----
#include "b.h"
#include "a.h"

int main() { A a; return a.b.x; }
----

. Встретили `#include "b.h"`, открыли `b.h`, отметили.
. Внутри `b.h` встретили `#include "a.h"`, открыли `a.h`, отметили.
. Внутри `a.h` встретили `#include "b.h"`. Файл **уже отмечен**, разворачивается в пустоту. И вот здесь ловушка: `b.h` отмечен, но его тело ещё не выполнено, мы находимся в его середине.
. Тело `a.h`: `struct A { B b; };`. А тип `B` ещё *не объявлен*.

[,text]
----
a.h:5:5: error: 'B' does not name a type
    5 |     B b;
      |     ^
----

Итог единицы трансляции:

[,cpp]
----
// тело a.h выполнилось РАНЬШЕ тела b.h
struct A { B b; };   // <-- B здесь неизвестен
struct B { int x; };
int main() { ... }
----

Не собирается. Исходники не менялись, поменялся *порядок двух строк* в третьем файле.

=== Почему так вышло

Ключевой момент, который надо уметь проговорить: страж включения (`#pragma once` или `#ifndef`) отмечает файл как обработанный **в момент входа в него**, а не в момент выхода. Это обязательно должно быть так, иначе рекурсивное включение зациклилось бы навсегда.

Следствие: при циклическом включении один из двух файлов *всегда* получит пустышку вместо второго. Какой именно - зависит от того, с какого файла начали. Отсюда и зависимость от порядка строк.

Тот же разбор через классические стражи, чтобы было видно механику явно:

[,cpp]
----
// b.h
#ifndef B_H_          // не определён, заходим
#define B_H_          // отметили СРАЗУ, тело ещё не выполнено
#include "a.h"        // ...а внутри a.h проверка #ifndef B_H_ уже провалится
struct B { int x; };
#endif
----

Проверить всё это можно, не гадая:

[,console]
----
$ g++ -E main.cpp | grep -v '^#' | grep -v '^$'    <1>
----
<1> Посмотреть итоговую единицу трансляции без служебных строк с номерами. Порядок определений будет виден глазами.

=== Как чинить

К сожалению, просто переставить строки - плохая опция. Переставить строки это заклеить симптом: сборка будет держаться на том, что никто никогда не включит `b.h` первым, а через месяц кто-нибудь включит.

Чинить надо саму циклическую зависимость.

*Способ 1, основной: предварительное объявление (forward declaration).*

Полный тип нужен, только если компилятору надо знать *размер*: для поля по значению, наследования, `sizeof`, обращения к членам. Для указателя и ссылки размер известен всегда, хватит объявления.

[,cpp]
----
// a.h
#pragma once
struct B;              // достаточно, никакого #include

struct A {
    B* b;              // указатель, размер известен
};
----

Цикл разорван, `a.h` больше не включает `b.h` вообще. Полный `#include "b.h"` переезжает в `a.cpp`, где реально нужно разыменовывать указатель.

*Способ 2: пересмотреть дизайн.*

Если `A` и `B` действительно нуждаются друг в друге по значению, то это не проблема включений, а логическое противоречие:

[,cpp]
----
struct A { B b; };
struct B { A a; };     // sizeof(A) = sizeof(B) + ... = бесконечность
----

Такая пара типов невозможна в принципе, и компилятор прав. Кто-то из двоих обязан хранить указатель, ссылку или ничего.

*Способ 3: убрать лишние `#include` из заголовков.*

Общее правило: в заголовке включайте *минимум*, а тяжёлые включения переносите в `.cpp`. Заголовок должен тянуть за собой только то, без чего он не может быть разобран.

TIP: Проверить, что заголовок самодостаточен и при этом не тянет лишнего, можно грубой силой: собрать его отдельно как единственную TU.

[,console]
----
$ g++ -fsyntax-only -x c++ include/myproject/a.h
----

Если проходит - заголовок можно включать первым в любой файл, и он не сломается.
