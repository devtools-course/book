== Устройство проекта

=== Расширения файлов

Компилятор ориентируется на расширение, чтобы понять язык. Устоявшиеся варианты:

[cols="1,2,2"]
|===
|Расширение |Что |Комментарий

|`.c`
|Исходник C
|Единственный вариант

|`.cpp`
|Исходник C++
|Самый распространённый, безопасный выбор

|`.cc`
|Исходник C++
|Стиль Google, часто в Unix-проектах

|`.cxx`, `.C`
|Исходник C++
|Редко. Заглавная `.C` опасна: на macOS файловая система по умолчанию нечувствительна к регистру, и `.C` не отличается от `.c`

|`.h`
|Заголовок
|Исторически C, но в C++ используется постоянно

|`.hpp`
|Заголовок C++
|Явно говорит, что внутри C++

|`.hh`
|Заголовок C++
|Парный к `.cc`

|`.hxx`, `.tpp`, `.ipp`
|Заголовок, реализация шаблонов
|Для файлов, которые включаются в конце заголовка
|===

Про `.hh` против `.cc`: это просто согласованная пара из одной школы именования (Google, часть GNU-проектов). Другая распространённая пара - `.hpp` и `.cpp`. Третья - `.h` и `.cpp`, самая частая в реальности, хотя формально непоследовательная. Технической разницы нет: gcc одинаково соберёт `.cc` и `.cpp`. Важно только, чтобы внутри одного проекта было единообразно.

=== Структура каталогов

Типовая раскладка небольшого проекта:

[,text]
----
myproject/
├── CMakeLists.txt        сборка
├── Makefile
├── README.md
├── include/              публичные заголовки
│   └── myproject/        подкаталог с именем проекта!
│       ├── math.h
│       └── utils.h
├── src/                  реализация и приватные заголовки
│   ├── main.cpp
│   ├── math.cpp
│   ├── utils.cpp
│   └── internal.h        не для внешних пользователей
├── tests/
│   └── test_math.cpp
├── third_party/          чужой код и сабмодули
└── build/                артефакты сборки, в .gitignore
----

Несколько правил, за которыми стоит настоящая боль:

Публичные заголовки в отдельном каталоге::
Так `-Iinclude` открывает наружу ровно то, что вы хотели открыть, и ни строчкой больше. Приватные заголовки лежат рядом с реализацией в `src/`.

Подкаталог с именем проекта внутри `include/`::
Тогда пользователь пишет `#include <myproject/math.h>`, а не `#include <math.h>`. Второе рано или поздно столкнётся с системным заголовком, и отлаживать это будет очень грустно.

Сборка отдельно от исходников::
Каталог `build/` целиком в `.gitignore`. Это называется out-of-source build: удалить его можно в любой момент, а `git status` остаётся чистым.

Каждый `.cpp` включает свой заголовок первым::
Если `math.cpp` начинается с `#include "myproject/math.h"`, то заголовок гарантированно самодостаточен: он не полагается на то, что кто-то до него уже включил нужные зависимости. Это дешёвая автоматическая проверка.

=== Порядок включений

Общепринятый порядок (стиль Google, но прижился шире):

[,cpp]
----
#include "myproject/math.h"    // 1. свой заголовок

#include <cmath>               // 2. стандартная библиотека
#include <vector>

#include <boost/asio.hpp>      // 3. сторонние библиотеки

#include "myproject/utils.h"   // 4. остальное своё
#include "internal.h"
----

Смысл именно в первом пункте: свой заголовок идёт до всего остального, поэтому если он забыл включить `<vector>`, сборка сломается сразу, а не через полгода у случайного пользователя.
