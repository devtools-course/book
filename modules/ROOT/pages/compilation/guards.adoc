== `#pragma`

`#pragma` это способ сказать конкретному компилятору что-то нестандартное. Стандарт разрешает директиву, но не описывает содержимое: любой компилятор понимает свой набор прагм и обязан молча игнорировать незнакомые.

Самая известная:

[,cpp]
----
#pragma once
----

Она заменяет header guard (о них ниже). Формально нестандартная, фактически поддерживается всеми живыми компиляторами.

Другие полезные:

[,cpp]
----
#pragma GCC diagnostic push                            // запомнить настройки предупреждений
#pragma GCC diagnostic ignored "-Wunused-variable"     // временно выключить одно
// ... код, на который ругаться не надо
#pragma GCC diagnostic pop                             // вернуть как было

#pragma pack(push, 1)                                  // выключить выравнивание полей
struct Packed { char a; int b; };                      // sizeof == 5, а не 8
#pragma pack(pop)

#pragma omp parallel for                               // директива OpenMP
for (int i = 0; i < n; ++i) { ... }
----

NOTE: `#pragma pack` из примера меняет физическую раскладку структуры. Это нужно, когда структура описывает формат данных на диске или в сети, и категорически не нужно «для экономии памяти»: невыровненный доступ на многих архитектурах медленнее, а на некоторых просто падает.

Есть ещё оператор `_Pragma("...")`, который делает то же самое, но является выражением, а не директивой, и потому может быть получен из макроса. Директиву `#pragma` из макроса выдать нельзя, а `_Pragma` можно.

== Header guards и почему они нужны

Раз `#include` вставляет текст буквально, ничто не мешает вставить один и тот же файл дважды. А второе объявление структуры это ошибка:

[,text]
----
error: redefinition of 'struct Point'
----

Так происходит легко и незаметно: `main.cpp` включает `a.h` и `b.h`, а `b.h` внутри себя тоже включает `a.h`. Никто не виноват, а файл приехал дважды.

Лечение - *страж включения* (include guard, header guard):

[,cpp]
----
#ifndef PROJECT_GEOMETRY_POINT_H_
#define PROJECT_GEOMETRY_POINT_H_

struct Point { int x, y; };

#endif  // PROJECT_GEOMETRY_POINT_H_
----

Механика: первый раз макрос не определён, условие проходит, макрос определяется, тело файла попадает в TU. Второй раз макрос уже определён, и *весь файл целиком* вырезается препроцессором.

Имя макроса должно быть уникальным на весь проект, поэтому в него принято закладывать путь к файлу. Имя `POINT_H` в большом проекте почти гарантированно с чем-нибудь столкнётся, и тогда один из заголовков молча перестанет включаться. Отлаживать это очень неприятно.

CAUTION: Не начинайте имя стража с подчёркивания и не используйте двойное подчёркивание внутри (`+_POINT_H+`, `+__POINT_H__+`). Такие имена стандарт резервирует за реализацией, и вы рискуете переопределить что-нибудь из внутренностей стандартной библиотеки и будет очень страшно.

Альтернатива - `#pragma once` одной строкой в начале файла:

[,cpp]
----
#pragma once

struct Point { int x, y; };
----

Сравнение:

[cols="1,2,2"]
|===
| |Header guard |`#pragma once`

|Стандартность
|В стандарте
|Нестандартна, но поддерживается везде

|Ошибки
|Можно опечататься в имени или скопировать чужое
|Ошибиться негде

|Скорость
|Компилятор всё равно открывает файл (современные умеют оптимизировать)
|Файл не открывается повторно

|Странные случаи
|Работает всегда
|Может сбоить, если один файл доступен по двум путям (симлинки, хардлинки, разные mount)
|===

На практике берите то, что принято в вашем проекте. Если проекта ещё нет, `#pragma once` проще и ошибиться в нём нельзя.
