== GNU Make

Собирать проект руками из десяти файлов утомительно, а из ста невозможно. Нужен инструмент, который знает зависимости и пересобирает только то, что реально изменилось. Классический такой инструмент - `make`.

Идея простая: `make` читает `Makefile`, где описаны *правила* вида «цель зависит от таких-то файлов и делается такой-то командой», и сравнивает *времена изменения* файлов. Если цель новее всех своих зависимостей, работа не нужна.

=== Синтаксис правила

[,make]
----
цель: зависимости
	команда
----

CAUTION: Команда обязана начинаться с *символа табуляции*, а не с пробелов. Это одна из самых известных претензий к make. Ошибка при этом выглядит совершенно не по делу: `Makefile:4: *** missing separator. Stop.` Настройте редактор так, чтобы он не превращал табы в пробелы в Makefile.

Прямолинейный вариант для трёх файлов:

[,make]
----
app: main.o utils.o math.o
	g++ main.o utils.o math.o -o app

main.o: main.cpp utils.h math.h
	g++ -c main.cpp -o main.o

utils.o: utils.cpp utils.h
	g++ -c utils.cpp -o utils.o

math.o: math.cpp math.h
	g++ -c math.cpp -o math.o

clean:
	rm -f *.o app
----

Что здесь происходит при `make app`: make видит, что `app` зависит от трёх объектников, рекурсивно проверяет каждый, и если, скажем, изменился только `utils.cpp`, пересоберёт `utils.o` и перелинкует `app`. Остальное трогать не будет. Ради этого всё и затевалось.

Обратите внимание, что зависимости от заголовков надо прописывать *руками*: make не знает про `#include`. Если забыть `utils.h` в зависимостях `main.o`, то после правки заголовка `main.o` не пересоберётся, и вы получите сборку из несогласованных объектников. Это классический источник «почистил, пересобрал, и всё заработало».

=== Переменные и автоматические переменные

[,make]
----
CXX      := g++
CXXFLAGS := -std=c++17 -Wall -Wextra -O2
LDFLAGS  := -L./lib
LDLIBS   := -lmytools

SRCS := main.cpp utils.cpp math.cpp
OBJS := $(SRCS:.cpp=.o)          # заменить расширение у каждого элемента
TARGET := app

$(TARGET): $(OBJS)
	$(CXX) $(OBJS) $(LDFLAGS) $(LDLIBS) -o $@

%.o: %.cpp                        # шаблонное правило для всех .cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

.PHONY: clean all
all: $(TARGET)

clean:
	rm -f $(OBJS) $(TARGET)
----

Автоматические переменные внутри команды:

`$@`::
Имя цели.

`$<`::
Первая зависимость.

`$^`::
Все зависимости, без повторов.

`$?`::
Только те зависимости, которые новее цели.

`.PHONY`::
Список целей, которые не являются файлами. Без этого `make clean` сломается ровно в тот день, когда в каталоге заведётся файл с именем `clean`: make решит, что цель уже готова, и ничего не сделает.

=== Автоматические зависимости от заголовков

Прописывать заголовки руками невозможно в реальном проекте. Правильное решение - попросить сам компилятор сгенерировать зависимости:

[,make]
----
CXXFLAGS += -MMD -MP           <1>
DEPS := $(OBJS:.o=.d)

%.o: %.cpp
	$(CXX) $(CXXFLAGS) -c $< -o $@

-include $(DEPS)               <2>
----
<1> `-MMD` заставляет gcc рядом с каждым `.o` положить файл `.d` со списком включённых заголовков в формате правила make. `-MP` добавляет фиктивные цели для самих заголовков, чтобы удаление заголовка не ломало сборку.
<2> Подключить эти файлы, если они есть. Ведущий минус означает «не ругаться, если файла нет»: при первой сборке их ещё не существует.

Полезные флаги самого make:

[,console]
----
$ make -j8            <1>
$ make -n             <2>
$ make -B             <3>
$ make --debug=b      <4>
----
<1> Собирать в 8 параллельных задач. На многоядерной машине ускорение почти линейное, потому что компиляция каждой TU независима.
<2> Показать команды, но не выполнять их.
<3> Пересобрать всё принудительно, игнорируя времена файлов.
<4> Объяснить, почему make решил пересобрать конкретную цель.

NOTE: `make` сегодня уже редко пишут руками для больших проектов: неудобно поддерживать, тяжело сделать переносимым между платформами, тяжело писать. Вместо этого пишут `CMakeLists.txt`, а CMake генерирует Makefile (или файлы для Ninja, Visual Studio, Xcode). Но понимать make всё равно надо: сгенерированное отлаживать всё равно вам, и модель «цель, зависимости, времена изменения» лежит в основе всех систем сборки.

Расскажу интересный случай: коллега написал Makefile, который скачивал библиотеку с GitHub и заменял ею системную. Мы долго не могли понять, почему у нас начали вылезать баги, хотя все вроде правильно. Его Makefile скачивал неверную библиотеку и портил драйвер системы. Мораль сей басни такова: надо писать Makefile очень аккуратно. Основано на реальных событиях. Вообще лучше писать сразу CMake.
