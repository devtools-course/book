== Библиотеки

=== Статическая библиотека

Статическая библиотека `.a` это просто *архив* объектных файлов. Никакой специальной обработки, обычный контейнер, немногим сложнее tar.

[,console]
----
$ g++ -c mathlib.cpp -o mathlib.o
$ g++ -c strlib.cpp -o strlib.o
$ ar rcs libmytools.a mathlib.o strlib.o     <1>

$ ar t libmytools.a                          <2>
mathlib.o
strlib.o

$ nm -C libmytools.a | head                  <3>
----
<1> `r` - добавить или заменить, `c` - создать не ругаясь, `s` - записать индекс символов.
<2> Показать содержимое архива.
<3> Символы по всем объектникам архива.

Использование:

[,console]
----
$ g++ main.cpp -L. -lmytools -o app
----

Здесь `-L.` добавляет текущий каталог к путям поиска, а `-lmytools` просит библиотеку. Обратите внимание на именование: по `-lmytools` линковщик ищет файл `libmytools.a` или `libmytools.so`. Префикс `lib` и расширение он добавляет сам, поэтому библиотеку нельзя назвать как попало.

=== Динамическая библиотека

[,console]
----
$ g++ -c -fPIC mathlib.cpp -o mathlib.o                  <1>
$ g++ -shared mathlib.o -o libmytools.so                 <2>
$ g++ main.cpp -L. -lmytools -Wl,-rpath,'$ORIGIN' -o app <3>
----
<1> `-fPIC` обязателен, объяснение ниже.
<2> `-shared` просит линковщик сделать разделяемую библиотеку, а не исполняемый файл.
<3> Плюс путь для загрузчика, иначе при запуске будет `not found`.

=== Зачем нужен `-fPIC`

*PIC* это Position Independent Code, позиционно-независимый код.

Проблема: одна и та же `libc.so` подгружается в сотни процессов, и в каждом она может оказаться по *разному* адресу (в том числе потому, что современные системы специально рандомизируют адреса, это ASLR). Если бы в коде библиотеки были зашиты абсолютные адреса, её пришлось бы править при каждой загрузке, а значит, страницы памяти нельзя было бы разделять между процессами, и весь смысл разделяемой библиотеки исчез бы.

Решение: генерировать код, который работает по любому адресу. Все обращения к глобальным данным идут не по абсолютному адресу, а через таблицу (GOT, Global Offset Table), а вызовы внешних функций через переходник (PLT, Procedure Linkage Table). Таблицы у каждого процесса свои и маленькие, а сам код общий, неизменяемый и разделяемый.

Забыли `-fPIC` - получите такое:

[,text]
----
/usr/bin/ld: mathlib.o: relocation R_X86_64_32S against '.rodata' can not be used
when making a shared object; recompile with -fPIC
----

Линковщик прямым текстом говорит, что делать. Для статических библиотек `-fPIC` не нужен, там код попадает в конечный бинарь и правится на месте.

=== Версионирование и soname

В системе вы увидите цепочку файлов и симлинков:

[,console]
----
$ ls -l /usr/lib/x86_64-linux-gnu/libfoo*
libfoo.so -> libfoo.so.1.2.3        <1>
libfoo.so.1 -> libfoo.so.1.2.3      <2>
libfoo.so.1.2.3                     <3>
----
<1> Симлинк для линковщика: по нему находится библиотека при сборке с `-lfoo`.
<2> Симлинк по *soname*, по нему библиотеку ищет загрузчик при запуске.
<3> Настоящий файл с полной версией.

*soname* (`-Wl,-soname,libfoo.so.1`) - это имя, которое записывается внутрь библиотеки и попадает в зависимости программы. Смысл в том, что старший номер меняется при *несовместимом* изменении интерфейса. Программа, собранная с `libfoo.so.1`, продолжит работать после обновления до `1.2.4`, но не подхватит `libfoo.so.2`.

[,console]
----
$ g++ -shared -fPIC -Wl,-soname,libfoo.so.1 foo.o -o libfoo.so.1.2.3
$ ln -sf libfoo.so.1.2.3 libfoo.so.1
$ ln -sf libfoo.so.1 libfoo.so
$ objdump -p libfoo.so.1.2.3 | grep SONAME
  SONAME               libfoo.so.1
----
