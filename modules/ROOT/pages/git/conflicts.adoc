== 3-way merge

При merge Git ищет *общего предка* двух веток (base) и смотрит, как изменился файл в каждой ветке относительно предка: подсчитывает диффы коммитов к нему.

.3 way merge algorithn
image::git/3way-merge.png[]

Три случая:

. В одной ветке файл изменился, в другой нет  --  берется измененная версия. Никакого конфликта.
. В обеих ветках файл изменился, но в *разных местах*  --  Git применяет оба набора изменений. Тоже без конфликта, это называется *auto-merge*.
. В обеих ветках изменения затронули *соседние строки*  --  Git не знает, какой вариант правильный, и объявляет конфликт.

== Виды конфликтов

При наличии изменений файлов с одинаковым именем Git потенциально будет выкидывать ошибку. Основными исключениями будут:

* Изменение разрешения на исполнение файла (`chmod +x`)
* Изменение содержимого файла (с исключениями)

Поэтому если на одной ветке файл был удален, а на другой изменено его содержимое, то случится конфликт `modify/delete`.

Конфликтные места помечаются в файле:

[,git-conflict]
----
<<<<<<< HEAD
print("Hello, world!")
=======
print("Привет, мир!")
>>>>>>> feature-x
----

* Между `<<<<<<< HEAD` и `=======`  --  текущий вариант.
* Между `=======` и `>>>>>>> feature-x`  --  вариант из ветки feature-x.

Как разрешить:

. Открыть файл, руками выбирать нужный вариант (или скомбинировать), также важно не забыть удалить все три маркера.
. `git add FILE`  --  сообщить Git, что конфликт разрешен.
. `git commit`  --  завершить merge.

Если запутались и хотите откатить все:

[,console]
----
$ git merge --abort     <1>
$ git rebase --abort    <2>
----
<1> Отменить незавершенный merge.
<2> То же для незавершенного rebase.

[TIP]
====
Очень полезная опция  --  включить трехсторонний вид конфликтов:

[,console]
----
$ git config --global merge.conflictstyle diff3
----

После этого маркеры будут выглядеть так:

[,git-conflict]
----
<<<<<<< HEAD
print("Hello, world!")
||||||| merged common ancestors
print("hello")
=======
print("Привет, мир!")
>>>>>>> feature-x
----

Средний блок  --  оригинальная строка до расхождения. Гораздо проще понять, что каждая ветка меняла.

== Мерж-производные команды

=== Cherry-pick

Находясь на коммите `A` пытаемся сделать черрипик коммита `B`.

image::git/3w-cherry.png[]

Ours   : `HEAD` +
Theirs : `B` +
Base   : `B^`

=== Revert

Находясь на коммите `A` пытаемся сделать реверт коммита `B`.

image::git/3w-revert.png[]

Ours   : `HEAD` +
Theirs : `B^` +
Base   : `B`

_По сути `revert`  --  это `cherry-pick` наоборот: вместо того, чтобы смотреть изменения к родителю коммита, мы смотрим на изменения к коммиту относительно его родителя._

== Rebase

Ребейз же является последовательным черрипиком коммитов: представьте, что на вершине ветки, на которую делается ребейз, создается временная ветка. Далее она последовательно черрипикает все коммиты из исходной ветки, после чего теперь она назначается исходной веткой.
