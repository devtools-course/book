= Объединение изменений веток
:page-authors: Виктория Попова, Иван Калинин
:description: Git. Объединение изменений веток

Для того чтобы перенести изменения из одной ветки в другую существует три основных способа. Разница между ними это одна из самых частых тем на собеседованиях, поэтому разберем подробно.

== Merge

image::git/merge.png[]

Объединяет две ветки, создавая новый *merge-коммит* с двумя родителями.

Важно понимать направление: изменения всегда вливаются *в текущую ветку*. Поэтому сначала переключаемся туда, куда мерж, а имя ветки в команде  --  это то, откуда берем изменения:

[,console]
----
$ git switch main                     <1>
$ git merge feature-x                 <2>
Merge made by the 'ort' strategy.
 app/login.py | 12 ++++++++++++
 1 file changed, 12 insertions(+)
----
<1> Переходим в ветку-приемник: менять будем `main`.
<2> Вливаем в нее `feature-x`. То есть `feature-x \-> main`; сама `feature-x` при этом не меняется вообще.

Посмотреть, что получилось:

[,console]
----
$ git log --oneline --graph -3
*   9c1f0aa (HEAD -> main) Merge branch 'feature-x' into main   <1>
|\
| * 3f2a1b0 (feature-x) Add login form                          <2>
* | 7d4e8c2 Fix typo in README                                  <3>
|/
----
<1> Merge-коммит: он появился только в `main`, и у него два родителя.
<2> Первый родитель  --  то, на чем стояла `main` до мержа.
<3> Второй родитель  --  вершина `feature-x`.

Если `main` не двигалась с момента ответвления `feature-x`, merge будет *fast-forward*: `main` просто «догонит» `feature-x`, никакого нового коммита не создастся. Если `main` тоже уходила вперед  --  создастся merge-коммит.

Плюс merge: сохраняет полную историю «как было на самом деле». Минус: история становится ветвистой, и в `git log` без графа выглядит запутанно.

TIP: Если в вашей команде следуют gitflow, то fast-forward может мешать видеть моменты вливания фича-бранчей. Как следствие, может быть полезным использовать флаг `--no-ff`, который предотвращает fast-forward.

=== Мерж нескольких веток сразу

Родителей у merge-коммита может быть и больше двух. `git merge` принимает сколько угодно веток  --  такой мерж называется *octopus*:

[,console]
----
$ git switch main
$ git merge feature-a feature-b feature-c
Trying simple merge with feature-a
Trying simple merge with feature-b
Trying simple merge with feature-c
Merge made by the 'octopus' strategy.
 a.py | 3 +++
 b.py | 5 +++++
 c.py | 2 ++
 3 files changed, 10 insertions(+)

$ git log --oneline --graph -4
*-----.   4b7c9d1 (HEAD -> main) Merge branches 'feature-a', 'feature-b' and 'feature-c'
|\ \ \
| | | * 1a2b3c4 (feature-c) Add c
| | * | 5d6e7f8 (feature-b) Add b
| * | | 9a8b7c6 (feature-a) Add a
|/ / /
----

Получается один коммит с четырьмя родителями вместо трех отдельных мержей.

CAUTION: Octopus работает только если *ни в одной* из веток нет конфликтов  --  разрешать конфликты эта стратегия не умеет и просто откажется мержить: `Should not be doing an octopus`. Тогда придется сливать ветки по одной обычным merge. На практике octopus встречается редко: история с ним читается тяжелее, а откатить такой мерж сложнее.

=== Мерж несвязных веток

Так как мерж ищет общего предка веток, то в условии его отсутствия он откажется работать:

[,console]
----
$ git merge i/main
fatal: refusing to merge unrelated histories
----

Такое может возникать, когда вы добавляете новый ремоут и пытает вмержить изменения из него в уже существующую локальную ветку. В таком случае поможет флаг `--allow-unrelated-histories`:

[,console]
----
$ git merge --allow-unrelated-histories i/main
Merge made by the 'ort' strategy.
 LICENSE                         | 437 +++++++++++++++++++
 README.adoc                     | 114 ++++++
 2 files changed, 551 insertions(+)
 create mode 100644 LICENSE
 create mode 100644 README.adoc
$ git log --oneline --all --graph
* 6e6e8bf (HEAD -> main) Merge remote-tracking branch 'i/main'
|\
| * 6274c31 (i/main, i/HEAD) Update README.adoc
| * 50a0f44 Add tests
| * 37743bc Task description
* 474b9a4 (origin/main, origin/HEAD) 1
* e171b95 initial commit
----

=== Стратегии мержа

Выше уже мы увидели две стратегии мержа: `ort` (дефолтная) и `octopus`

Стратегия `ort` основана на алгоритме xref:git/conflicts.adoc[3-way merge], а `octopus` разрешает мержить больше 2 веток. Также существует стратегия `ours`, которая просто игнорирует чужие изменения и оставляет изменения текущей ветки.

Выбрать стратегию можно передав через флаг `-s _STRATEGY_`.

Дополнительно у стратегии `ort` есть параметры разрешения конфликтов:

ours::
В случае конфликтующих изменений будет выбрано изменение из текущей ветки. *Важно:* не путайте со стратегией `ours`. Так при наличии в файле двух изменений из другой ветки, одно из которых конфликтует, а второе  --  нет, первое будет затерто изменением нашей ветки, а второе удачно слито

theirs::
Аналогично прошлому, но выбираются изменения из другой ветки

Их передать можно через флаг `-X`

NOTE: Передать эти параметры можно также всем merge-производным командам

== Rebase

image::git/rebase.png[]
«Отрывает» ваши коммиты и переносит их поверх другой ветки:

[,console]
----
$ git switch feature-x
$ git rebase main
----

=== Interactive rebase

Самая мощная штука, которая есть в Git. Позволяет редактировать, объединять, переставлять, удалять коммиты:

[,console]
----
$ git rebase -i HEAD~5
----

Откроется редактор со списком последних 5 коммитов и командами:

[,git-rebase]
----
pick 57fbf09 # 2
pick d721a76 # abc
pick 083fc56 # 4
pick 30f56e4 # 6
pick a853197 # 9
pick a8dc20a # 10
pick d27736c # 1
pick e171b95 # 1
pick 474b9a4 # 1

# Rebase 5d11a06..474b9a4 onto 5d11a06 (9 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# ...
----

* `pick`  --  оставить как есть;
* `reword`  --  изменить сообщение;
* `edit`  --  остановиться на этом коммите, чтобы что-то поменять в файлах;
* `squash`  --  слить с предыдущим (сообщения объединятся);
* `fixup`  --  как `squash`, но сообщение выбросить (часто именно то, что нужно);
* `drop`  --  удалить коммит;
* поменять местами строки  --  поменяются местами и коммиты.

Чтобы применить команду, нужно просто заменить `pick` на выбранное действие.

TIP: Вместо полных названий команд можно использовать однобуквенные сообщения

Полезно перед созданием Pull Request: подчистить историю, слить мелкие «fix» коммиты, переформулировать сообщения.

== Cherry-pick

image::git/cherry.png[]
Взять один конкретный коммит и применить его к текущей ветке:

[,console]
----
$ git cherry-pick 3f2a1b0
$ git cherry-pick 3f2a1b0..c4d5e6f   <1>
----
<1> Диапазон коммитов.

Полезно, когда, например, нужно перенести один хотфикс из main в старую релизную ветку, но остальные изменения из main трогать нельзя.

== Что когда использовать (кратко)

* Ваша ветка локальная или живет только в вашем форке  --  смело `rebase`.
* Ветка общая, на нее смотрит кто-то еще  --  только `merge`. Иначе сломаете коллегам историю.
* Нужен один конкретный коммит из другой ветки  --  `cherry-pick`.

CAUTION: `rebase` и `cherry-pick` создают *новые* коммиты с новыми хэшами. Если делать это с уже запушенными коммитами, потом придется `push --force`, что может иметь определенные последствия.
